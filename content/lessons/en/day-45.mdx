## Intro

<En>
Real APIs are slow, rate-limited, unreliable, and sometimes cost money per call. Mocking lets you replace a real HTTP server with a fake one that returns pre-defined responses. This makes tests fast, deterministic, and independent of external services. `responses` is the most popular Python library for mocking HTTP calls made with the `requests` library.
</En>
<Vi>
Các API thực chậm, bị giới hạn tốc độ, không đáng tin cậy và đôi khi tốn tiền mỗi lần gọi. Mock cho phép bạn thay thế HTTP server thực bằng server giả trả về các response được định nghĩa trước. Điều này làm cho test nhanh, xác định và độc lập với các dịch vụ bên ngoài. `responses` là thư viện Python phổ biến nhất để mock các HTTP call được thực hiện với thư viện `requests`.
</Vi>

## Concept

<En>
**When to mock vs when to test against a real API:**

| Use mocks when | Use real API when |
|----------------|------------------|
| Testing unit logic (parsing, validation) | Running integration or E2E tests |
| Third-party API is rate-limited or costly | You own the API and control the environment |
| Response scenarios are hard to reproduce (e.g., 500 error, timeout) | Contract testing (verifying the schema) |
| CI must be fast and offline-capable | Acceptance testing before release |

**The `responses` library:**
```bash
pip install responses
```

**What `@responses.activate` does:**
- Intercepts all `requests` calls within the decorated function
- Any unregistered URL raises `ConnectionError` — preventing accidental real network calls
- After the test exits (pass or fail), all registered mocks are cleared automatically
- You can also use it as a context manager: `with responses.RequestsMock() as rsps:`

**Mocking error scenarios:**

The `responses` library supports three kinds of error simulation:

1. **HTTP error responses** — return a non-2xx status code with a body
2. **Network exceptions** — pass a real exception class via `body=` to simulate connection problems
3. **Sequential responses** — register multiple `responses.add()` calls for the same URL to return different results on each call

**Mocking at HTTP level vs mocking a function:**

| Approach | Library | What it replaces | Best for |
|----------|---------|-----------------|----------|
| HTTP-level mock | `responses` | The actual TCP/HTTP layer | Testing code that calls `requests.get/post/...` |
| Function mock | `unittest.mock.patch` | A Python function or method | Testing code that calls a helper or service class |

When your code calls `requests.get()` directly, use `responses`. When your code calls a method on a wrapper class you control, `unittest.mock.patch` is simpler. Both approaches produce isolated tests — they just operate at different abstraction levels.
</En>
<Vi>
**Khi nào mock vs khi nào test với API thực:**

| Dùng mock khi | Dùng API thực khi |
|----------------|------------------|
| Kiểm thử logic đơn vị (phân tích, xác thực) | Chạy test tích hợp hoặc E2E |
| API bên thứ ba bị giới hạn hoặc tốn tiền | Bạn sở hữu API và kiểm soát môi trường |
| Kịch bản response khó tái hiện (lỗi 500, timeout) | Contract testing (xác minh schema) |
| CI phải nhanh và có thể chạy offline | Acceptance testing trước khi phát hành |

**Thư viện `responses`:**
```bash
pip install responses
```

**`@responses.activate` làm gì:**
- Chặn tất cả các `requests` call trong function được decorate
- Mọi URL chưa được đăng ký sẽ ném `ConnectionError` — ngăn các lần gọi mạng thực tình cờ
- Sau khi test kết thúc (pass hay fail), tất cả các mock đã đăng ký được xoá tự động
- Cũng có thể dùng như context manager: `with responses.RequestsMock() as rsps:`

**Mock các kịch bản lỗi:**

Thư viện `responses` hỗ trợ ba loại mô phỏng lỗi:

1. **HTTP error response** — trả về status code không phải 2xx kèm body
2. **Network exception** — truyền class exception thực qua `body=` để mô phỏng sự cố kết nối
3. **Response tuần tự** — đăng ký nhiều lần `responses.add()` cho cùng URL để trả về kết quả khác nhau mỗi lần gọi

**Mock ở tầng HTTP vs mock một function:**

| Cách tiếp cận | Thư viện | Thay thế gì | Dùng tốt nhất khi |
|----------|---------|-----------------|----------|
| Mock tầng HTTP | `responses` | Tầng TCP/HTTP thực | Code gọi `requests.get/post/...` trực tiếp |
| Mock function | `unittest.mock.patch` | Một function hoặc method Python | Code gọi một helper hay service class |

Khi code gọi `requests.get()` trực tiếp, dùng `responses`. Khi code gọi method trên lớp wrapper bạn kiểm soát, `unittest.mock.patch` đơn giản hơn. Cả hai đều tạo ra test cô lập — chỉ khác ở tầng trừu tượng.
</Vi>

## Code / Demo

<En>

**Part 1 — Happy path and error status mocks**

</En>
<Vi>

**Phần 1 — Mock happy path và trạng thái lỗi**

</Vi>

```python
import requests
import responses
import pytest

BASE_URL = "https://api.example.com"

# --- Happy path mock ---
@responses.activate
def test_get_user_success():
    responses.add(
        responses.GET,
        f"{BASE_URL}/users/1",
        json={"id": 1, "email": "alice@example.com", "role": "admin"},
        status=200,
    )
    response = requests.get(f"{BASE_URL}/users/1")
    assert response.status_code == 200
    user = response.json()
    assert user["email"] == "alice@example.com"
    assert user["role"] == "admin"

# --- 404 mock ---
@responses.activate
def test_get_nonexistent_user():
    responses.add(
        responses.GET,
        f"{BASE_URL}/users/9999",
        json={"error": "User not found"},
        status=404,
    )
    response = requests.get(f"{BASE_URL}/users/9999")
    assert response.status_code == 404
    assert "not found" in response.json()["error"].lower()

# --- Server error mock ---
@responses.activate
def test_handles_server_error():
    responses.add(
        responses.GET,
        f"{BASE_URL}/users/1",
        json={"error": "Internal Server Error"},
        status=500,
    )
    response = requests.get(f"{BASE_URL}/users/1")
    assert response.status_code == 500
    assert not response.ok
```

**Phần 2 — Exception mạng và mock tuần tự**

</Vi>

```python
# --- Timeout mock ---
@responses.activate
def test_handles_timeout():
    responses.add(
        responses.GET,
        f"{BASE_URL}/users/1",
        body=requests.exceptions.Timeout(),
    )
    with pytest.raises(requests.exceptions.Timeout):
        requests.get(f"{BASE_URL}/users/1", timeout=5)

# --- Multiple mocks in sequence ---
@responses.activate
def test_create_then_get_user():
    responses.add(
        responses.POST,
        f"{BASE_URL}/users",
        json={"id": 42, "email": "bob@example.com"},
        status=201,
    )
    responses.add(
        responses.GET,
        f"{BASE_URL}/users/42",
        json={"id": 42, "email": "bob@example.com", "role": "viewer"},
        status=200,
    )
    # Create
    create_resp = requests.post(f"{BASE_URL}/users", json={"email": "bob@example.com"})
    assert create_resp.status_code == 201
    user_id = create_resp.json()["id"]

    # Retrieve
    get_resp = requests.get(f"{BASE_URL}/users/{user_id}")
    assert get_resp.status_code == 200
    assert get_resp.json()["id"] == user_id

# --- What happens when an unmocked URL is called ---
@responses.activate
def test_unmocked_url_raises_connection_error():
    # Only /users/1 is mocked — calling /users/2 should raise ConnectionError
    responses.add(responses.GET, f"{BASE_URL}/users/1", json={"id": 1}, status=200)
    with pytest.raises(Exception):  # ConnectionError is a subclass of Exception
        requests.get(f"{BASE_URL}/users/2")

print("All mock tests passed!")
```
