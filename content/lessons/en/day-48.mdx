## Concept

<En>
**What makes a portfolio-worthy API test project:**
1. Clear README explaining what the project tests and how to run it
2. Well-organised file structure (by resource, not by test type)
3. Schema validation on every GET response
4. Both positive and negative test coverage
5. CI that runs on every push
6. No hardcoded credentials (environment variables for sensitive config)
7. Tests are independent — each can run in isolation without depending on other tests

**Why API CI is simpler than Playwright CI:**
Playwright CI requires installing a full browser binary (Chromium, Firefox, or WebKit) which adds 100–500 MB and 30–120 seconds to every CI run. API tests need only Python and pip — no browser, no display server, no screenshot artifacts. This is why API test suites can run in under 30 seconds on a fresh CI runner.

**What `pytest --tb=short` does:**
Shows a short traceback instead of the full traceback on failure. On CI with many tests, full tracebacks become noisy. `--tb=short` shows just the assertion line and the 3–5 lines around it — enough to understand the failure without scrolling through 50 lines.

**What `if: always()` does in a GitHub Actions step:**
By default, a step is skipped if a previous step failed. `if: always()` forces the step to run regardless — this is how you ensure the "Upload test results" step runs even when tests fail. Without it, CI would not produce the XML report on failure — exactly when you need it most.

**Test coverage in the context of API testing:**
In code coverage, "coverage" means the percentage of source lines executed by tests. In API testing, "coverage" means the percentage of endpoint/method/scenario combinations tested:
- Which endpoints are tested? (`/posts`, `/users`, `/comments`)
- Which HTTP methods per endpoint? (GET, POST, PUT, PATCH, DELETE)
- Which scenarios? (happy path, 404, 400, 500, invalid input, boundary values)

A well-covered API test suite hits every endpoint, every supported method, and at least one negative scenario per method.

**What goes in a good API test project README:**
- One-sentence description of what API is under test
- Prerequisites (Python version, `pip install`)
- Installation: `pip install -r requirements.txt`
- How to run all tests: `pytest tests/ -v`
- How to run a single test: `pytest tests/test_posts.py::test_get_post`
- How to run with CI-style output: `pytest tests/ --tb=short --junit-xml=results.xml`
- CI badge (optional but professional)
- What is covered (endpoints, methods, schemas)
</En>
<Vi>
**Điều làm cho dự án API test xứng đáng portfolio:**
1. README rõ ràng giải thích dự án kiểm thử gì và cách chạy
2. Cấu trúc file có tổ chức tốt (theo tài nguyên, không theo loại test)
3. Xác thực schema trên mọi GET response
4. Bao phủ cả test tích cực và tiêu cực
5. CI chạy trên mỗi lần push
6. Không có credential được hardcode (biến môi trường cho cấu hình nhạy cảm)
7. Test độc lập — mỗi cái có thể chạy riêng lẻ mà không phụ thuộc vào test khác

**Tại sao CI cho API đơn giản hơn CI cho Playwright:**
CI Playwright yêu cầu cài đặt binary trình duyệt đầy đủ (Chromium, Firefox hoặc WebKit) thêm 100–500 MB và 30–120 giây vào mỗi lần chạy CI. Test API chỉ cần Python và pip — không có trình duyệt, không có display server, không có screenshot artifact. Đó là lý do tại sao test suite API có thể chạy trong dưới 30 giây trên CI runner mới.

**`pytest --tb=short` làm gì:**
Hiển thị traceback ngắn thay vì traceback đầy đủ khi thất bại. Trên CI với nhiều test, traceback đầy đủ trở nên nhiều nhiễu. `--tb=short` chỉ hiển thị dòng assertion và 3–5 dòng xung quanh — đủ để hiểu lỗi mà không cần cuộn qua 50 dòng.

**`if: always()` làm gì trong GitHub Actions:**
Theo mặc định, một step bị bỏ qua nếu step trước thất bại. `if: always()` buộc step chạy bất kể điều đó — đây là cách bạn đảm bảo step "Upload test results" chạy ngay cả khi test thất bại. Không có nó, CI sẽ không tạo ra báo cáo XML khi thất bại — chính xác là khi bạn cần nhất.

**Test coverage trong bối cảnh API testing:**
Trong code coverage, "coverage" có nghĩa là tỷ lệ phần trăm dòng code được thực thi bởi test. Trong API testing, "coverage" có nghĩa là tỷ lệ phần trăm kết hợp endpoint/method/kịch bản được kiểm thử:
- Endpoint nào được kiểm thử? (`/posts`, `/users`, `/comments`)
- HTTP method nào cho mỗi endpoint? (GET, POST, PUT, PATCH, DELETE)
- Kịch bản nào? (happy path, 404, 400, 500, input không hợp lệ, boundary value)

Một test suite API được bao phủ tốt kiểm thử mọi endpoint, mọi method được hỗ trợ và ít nhất một kịch bản tiêu cực cho mỗi method.

**Nội dung README tốt cho dự án API test:**
- Mô tả một câu về API nào đang được kiểm thử
- Prerequisites (phiên bản Python, `pip install`)
- Cài đặt: `pip install -r requirements.txt`
- Cách chạy tất cả test: `pytest tests/ -v`
- Cách chạy một test: `pytest tests/test_posts.py::test_get_post`
- Cách chạy với đầu ra kiểu CI: `pytest tests/ --tb=short --junit-xml=results.xml`
- CI badge (tùy chọn nhưng chuyên nghiệp)
- Những gì được bao phủ (endpoint, method, schema)
</Vi>

```python
# tests/test_negative.py
import pytest
import time
from api.client import ApiClient

def test_get_nonexistent_post(api: ApiClient):
    """404 for a post id that does not exist."""
    response = api.get("/posts/99999")
    assert response.status_code == 404

def test_get_nonexistent_user(api: ApiClient):
    """404 for a user id that does not exist."""
    response = api.get("/users/99999")
    assert response.status_code == 404

def test_get_comments_for_nonexistent_post(api: ApiClient):
    """JSONPlaceholder returns empty list for non-existent post — not a 404."""
    response = api.get("/posts/99999/comments")
    assert response.status_code == 200
    assert response.json() == []

@pytest.mark.parametrize("invalid_id", ["abc", "0", "-1", "!@#"])
def test_invalid_post_id_format(api: ApiClient, invalid_id: str):
    """400 or 404 for non-integer post IDs — server must not crash."""
    response = api.get(f"/posts/{invalid_id}")
    assert response.status_code in (400, 404), \
        f"Expected 4xx for id={invalid_id!r}, got {response.status_code}"

def test_empty_post_body(api: ApiClient):
    """POST with empty body — server must not return 500."""
    response = api.post("/posts", json={})
    # JSONPlaceholder is lenient; a real production API should return 400 or 422
    assert response.status_code != 500, "Server must not crash on empty body"

def test_response_time_is_acceptable(api: ApiClient):
    """Performance: GET /posts should respond in under 3 seconds."""
    start = time.time()
    response = api.get("/posts/1")
    elapsed = time.time() - start
    assert response.status_code == 200
    assert elapsed < 3.0, f"Response took {elapsed:.2f}s — too slow"

def test_content_type_header(api: ApiClient):
    """Every JSON API response must declare application/json content type."""
    response = api.get("/posts/1")
    content_type = response.headers.get("Content-Type", "")
    assert "application/json" in content_type, \
        f"Expected application/json, got: {content_type}"
```

**Phần 2 — GitHub Actions CI workflow và requirements**

</Vi>

```yaml
# .github/workflows/api-tests.yml
name: API Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  api-test:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python 3.11
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"   # caches ~/.cache/pip between runs — speeds up repeated CI runs

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run API tests
        run: pytest tests/ -v --tb=short --junit-xml=results.xml

      - name: Upload test results
        uses: actions/upload-artifact@v4
        if: always()   # run this step even if the test step above failed
        with:
          name: api-test-results
          path: results.xml
```
