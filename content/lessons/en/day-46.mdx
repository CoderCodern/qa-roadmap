## Intro

<En>
The most powerful tests combine API and UI — using the API to set up state quickly and cheaply, then using the UI to verify that the state is displayed correctly. This pattern avoids slow UI-driven setup and makes tests much more reliable. It's how senior QA engineers think about test architecture.
</En>
<Vi>
Các test mạnh mẽ nhất kết hợp API và UI — sử dụng API để thiết lập trạng thái nhanh chóng và rẻ, sau đó sử dụng UI để xác minh rằng trạng thái được hiển thị đúng. Mẫu này tránh thiết lập chậm do UI điều khiển và làm cho test đáng tin cậy hơn nhiều. Đây là cách các kỹ sư QA cấp senior nghĩ về kiến trúc test.
</Vi>

## Concept

<En>
**The hybrid test pattern — three layers:**

**1. API setup (fast, direct):**
Create test data via API calls. No browser needed. Runs in milliseconds. A direct POST to create a resource is 50–100x faster than navigating a form.

**2. UI verification (meaningful, realistic):**
Navigate to the page and verify the UI reflects the state set via API. This is the most valuable layer — it confirms that data created by the backend actually appears correctly for the user.

**3. API teardown (fast, clean):**
Delete test data via API after the test. Keeps the database in a known state. Never rely on other tests cleaning up after you.

**Why API setup beats UI setup:**
| Dimension | UI setup | API setup |
|-----------|---------|----------|
| Speed | ~5–10 seconds | ~0.1–0.5 seconds |
| Reliability | Can break with UI changes | Stable as long as API works |
| Dependencies | Requires login UI, forms, navigation | Just a request |
| Maintenance | High — every UI change may break setup | Low — API contracts change less often |

**When to prefer pure UI tests:**
- When you are testing the UI interaction itself (form validation, keyboard shortcuts, animations)
- When the feature has no API equivalent (client-side-only logic)
- When testing the full user journey from scratch is the acceptance criteria

**Injecting auth state from an API token:**
```python
# Option 1: cookie-based auth
context.add_cookies([{"name": "session", "value": token, "domain": "example.com", "path": "/"}])

# Option 2: header-based auth (Bearer token)
context.set_extra_http_headers({"Authorization": f"Bearer {token}"})
```
`context.set_extra_http_headers` adds the header to every HTTP request made by any page in that browser context — not just the first navigation.

**Fixture scope strategy:**
- Shared API session (auth token, base URL): `scope="session"` — created once per test run
- Browser context with auth state: `scope="function"` — fresh per test to avoid state leakage between tests
</En>
<Vi>
**Mẫu test hỗn hợp — ba lớp:**

**1. API setup (nhanh, trực tiếp):**
Tạo dữ liệu test qua API call. Không cần trình duyệt. Chạy trong mili giây. Một POST trực tiếp để tạo tài nguyên nhanh hơn 50–100 lần so với điều hướng qua form.

**2. UI verification (có ý nghĩa, thực tế):**
Điều hướng đến trang và xác minh UI phản ánh trạng thái được đặt qua API. Đây là lớp có giá trị nhất — nó xác nhận dữ liệu được tạo bởi backend thực sự hiển thị đúng cho người dùng.

**3. API teardown (nhanh, sạch):**
Xoá dữ liệu test qua API sau khi test. Giữ cơ sở dữ liệu ở trạng thái đã biết. Đừng bao giờ dựa vào các test khác để dọn dẹp sau bạn.

**Tại sao API setup đánh bại UI setup:**
| Khía cạnh | UI setup | API setup |
|-----------|---------|----------|
| Tốc độ | ~5–10 giây | ~0.1–0.5 giây |
| Độ tin cậy | Có thể vỡ với thay đổi UI | Ổn định miễn là API hoạt động |
| Phụ thuộc | Yêu cầu UI đăng nhập, form, điều hướng | Chỉ một request |
| Bảo trì | Cao — mọi thay đổi UI có thể phá vỡ setup | Thấp — contract API thay đổi ít hơn |

**Khi nào nên dùng pure UI test:**
- Khi bạn đang kiểm thử chính tương tác UI (xác thực form, phím tắt, animation)
- Khi tính năng không có API tương đương (logic chỉ phía client)
- Khi kiểm thử toàn bộ hành trình người dùng từ đầu là tiêu chí chấp nhận

**Inject auth state từ API token:**
```python
# Tùy chọn 1: auth dựa trên cookie
context.add_cookies([{"name": "session", "value": token, "domain": "example.com", "path": "/"}])

# Tùy chọn 2: auth dựa trên header (Bearer token)
context.set_extra_http_headers({"Authorization": f"Bearer {token}"})
```
`context.set_extra_http_headers` thêm header vào mọi HTTP request được thực hiện bởi bất kỳ trang nào trong browser context đó — không chỉ lần điều hướng đầu tiên.

**Chiến lược fixture scope:**
- Session API dùng chung (auth token, base URL): `scope="session"` — tạo một lần mỗi test run
- Browser context với auth state: `scope="function"` — mới cho mỗi test để tránh rò rỉ trạng thái
</Vi>

# tests/test_hybrid.py — combining API + Playwright UI tests

import requests
import pytest
from playwright.sync_api import Page, BrowserContext, expect

BASE_API = "https://jsonplaceholder.typicode.com"
BASE_UI = "https://demo.playwright.dev/todomvc"

# --- Pattern 1: UI action → verify via page state (simulating API check) ---
def test_ui_action_reflected_in_api_state(page: Page):
    """
    User adds a TodoMVC item via UI → verify via page state (simulating API check).
    Real version: add item via UI → GET /todos from API → assert item is there.
    """
    page.goto(BASE_UI)
    inp = page.get_by_placeholder("What needs to be done?")
    inp.fill("Learn API+UI hybrid testing")
    inp.press("Enter")

    # UI verification
    item = page.get_by_role("listitem").filter(has_text="Learn API+UI hybrid testing")
    expect(item).to_be_visible()

    # Simulated API check (in real projects: requests.get("/todos") and assert it's there)
    item_count = page.get_by_role("listitem").count()
    assert item_count >= 1
    print(f"Item count after UI action: {item_count}")

# --- Pattern 2: API creates data → UI displays it ---
def test_api_data_displayed_in_browser(page: Page):
    """
    API creates a post → verify via another API call (simulating UI display verification).
    Demonstrates the setup-via-API pattern.
    In a real app: after API setup, page.goto(f"/posts/{id}") and assert the title is visible.
    """
    # 1. Create via API
    payload = {"title": "Hybrid Test Post", "body": "Created by API", "userId": 1}
    api_response = requests.post(f"{BASE_API}/posts", json=payload)
    assert api_response.status_code == 201
    created_post = api_response.json()
    print(f"Created post id: {created_post['id']}")

    # 2. Verify via another API call (simulating UI verification)
    get_response = requests.get(f"{BASE_API}/posts/{created_post['id']}")
    assert get_response.status_code == 200
    assert get_response.json()["title"] == "Hybrid Test Post"

    # In a real app with a live backend:

def test_inject_auth_state(context: BrowserContext):
    """
    Get auth token from API → inject into browser context → access protected UI.
    This avoids clicking through a login form in every test.
    """
    # Simulated: in a real project you would POST to /auth/login
    fake_token = "test-bearer-token-123"

    # Inject into browser context so ALL pages in this context send the header
    context.set_extra_http_headers({"Authorization": f"Bearer {fake_token}"})

    page = context.new_page()
    page.goto(BASE_UI)
    # In a real app: navigate to /dashboard — it loads because the auth header is present
    assert page.url.startswith("https://")
    print("Auth injected into browser context successfully")

# --- Pattern 4: Full 3-layer hybrid test with teardown ---
def test_full_hybrid_create_verify_delete(page: Page):
    """
    3-layer hybrid: API setup → UI verify → API teardown.
    This is the gold standard for API+UI integration tests.
    """
    # Layer 1: API setup — create the resource
    payload = {"title": "Portfolio Project", "body": "Built in Phase 4", "userId": 1}
    create_resp = requests.post(f"{BASE_API}/posts", json=payload)
    assert create_resp.status_code == 201
    resource_id = create_resp.json()["id"]

    try:
        # Layer 2: UI verification — navigate and confirm data is visible
        # JSONPlaceholder has no real UI, so we verify via a second API call here.
        # Replace with: page.goto(f"{BASE_UI}/posts/{resource_id}") in a real app.
        verify_resp = requests.get(f"{BASE_API}/posts/{resource_id}")
        assert verify_resp.status_code == 200
        assert verify_resp.json()["title"] == "Portfolio Project"
