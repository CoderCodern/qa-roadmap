## Intro

<En>
A test suite that produces no report is only half-useful. Stakeholders, developers, and product managers need to see test results in a readable format — not raw terminal output. Allure is the most widely adopted test reporting framework for Python. It produces interactive HTML reports with charts, step-by-step breakdowns, screenshots, and attachments. Today you integrate Allure into your capstone framework and learn why the annotations matter for debugging at scale — not just for presentation.
</En>
<Vi>
Một bộ test không tạo ra báo cáo chỉ hữu ích một nửa. Các bên liên quan, developer và quản lý sản phẩm cần xem kết quả test theo định dạng dễ đọc — không phải đầu ra terminal thô. Allure là framework báo cáo test được áp dụng rộng rãi nhất cho Python. Nó tạo ra các báo cáo HTML tương tác với biểu đồ, phân tích từng bước, ảnh chụp màn hình và tệp đính kèm. Hôm nay bạn tích hợp Allure vào capstone framework và tìm hiểu tại sao các annotation quan trọng cho việc debug ở quy mô lớn — không chỉ cho mục đích trình bày.

## Concept

<En>

**Installing Allure — two separate pieces:**

```bash
# 1. The pytest plugin (Python side — writes raw result JSON)
pip install allure-pytest

# 2. The Allure CLI (Java-based — generates HTML from JSON)
# macOS:
brew install allure
# Windows (Scoop):
scoop install allure
# Linux / CI (manual):
# Download from https://github.com/allure-framework/allure2/releases
# Extract and add bin/ to your PATH
```

**Why two pieces?** pytest with `allure-pytest` writes raw JSON files into an `allure-results/` directory after each test run. Those JSON files contain every test's status, steps, attachments, and labels. The Allure CLI then reads those JSON files and generates the final HTML report. This separation means you can re-generate the HTML from the same result files as many times as you like — without re-running the tests.

**Generating and viewing reports:**

```bash
# Step 1: run tests and write raw results
pytest tests/ --alluredir=allure-results

# Step 2a: development — generates HTML and opens browser automatically
allure serve allure-results

# Step 2b: CI — generates static HTML into allure-report/ without opening a browser
allure generate allure-results -o allure-report --clean
```

`allure serve` is for local development: it starts a temporary web server, generates the HTML, and opens it. `allure generate` is for CI pipelines where there is no browser — it writes the HTML to disk so you can upload it as a build artifact.

**The Allure label hierarchy — epic → feature → story:**

```
epic: "Blog API"
 └── feature: "Posts"
      ├── story: "Read"   — test_get_post, test_get_nonexistent_post
      └── story: "Create" — test_create_post
```

These three labels form the "Behaviours" view in the Allure report — a product-readable hierarchy. A stakeholder who has never seen the code can navigate to "Blog API → Posts → Create" and see exactly which scenarios pass and which fail. Without these labels, the report shows raw file paths, which only developers understand.

Why is this useful in practice? When you have 300 tests across a large suite, a plain list of test names in alphabetical order is nearly useless for root cause analysis. The hierarchy lets you spot that "User Authentication → Login → OAuth" has 3 failures in one build while "User Authentication → Login → Username-Password" has none — which immediately tells you the OAuth implementation broke, not the entire login flow.

**Severity levels — and why they affect triage:**

```python
allure.severity_level.BLOCKER   # system is unusable — deploy must stop
allure.severity_level.CRITICAL  # core business flow broken — must fix today
allure.severity_level.NORMAL    # standard functionality impaired — fix in sprint
allure.severity_level.MINOR     # edge case failure — plan for next sprint
allure.severity_level.TRIVIAL   # cosmetic or negligible — backlog
```

Severity is not just decoration. In CI, you can configure your pipeline to fail the build only on BLOCKER and CRITICAL failures and let MINOR/TRIVIAL failures produce warnings. This means a CSS pixel offset in the UI does not block a backend API deployment. Without severity labels, every failure is treated equally — which either causes alert fatigue (ignore everything because it always fails) or false urgency (panic about a trivial issue).

**Why `allure.step()` is more valuable than raw assertions for debugging:**

When a raw assertion fails in a 40-line test function, the error message is `AssertionError`. You read the traceback, find the line number, correlate it with the test logic, and eventually understand what happened. In a CI report that email was three hours ago, that is expensive.

With `allure.step("Verify status is 201")`, the report shows "Step 4 — Verify status is 201 — FAILED", and every step before it shows PASSED. The analyst immediately knows the request was sent (step 2 passed), the response was received (step 3 passed), but the status was wrong (step 4 failed). The narrowing of the failure to a specific named step eliminates most of the detective work.

**`allure.attach()` — persisting evidence for post-mortem analysis:**

Attaching the response body, screenshots, or log files to a test result means you can debug a failure hours or days later without re-running the test. For a test that fails intermittently (flaky test) this is especially valuable — you may never reproduce it on demand.

**categories.json — grouping failures by type:**

You can create a `categories.json` file in your `allure-results/` directory to define custom failure categories:

```json
[
  {
    "name": "Network errors",
    "messageRegex": ".*ConnectionError.*",
    "matchedStatuses": ["broken"]
  },
  {
    "name": "Schema violations",
    "messageRegex": ".*Schema validation failed.*",
    "matchedStatuses": ["failed"]
  }
]
```

Without categories, all failures pile into a single "Product Defects" bucket. With categories, the Allure "Categories" tab separates "Network errors" (infrastructure issues, not code bugs) from "Schema violations" (API contract changes) from "Assertion failures" (genuine regressions). This separates noise from signal in large suites.

**The full Allure report structure:**

- **Overview** — pass/fail/broken counts, trend chart across builds
- **Suites** — test hierarchy by file → class → function
- **Behaviours** — grouped by epic → feature → story (product-readable)
- **Categories** — failed tests grouped by failure type (from categories.json)
- **Timeline** — test execution order and duration (shows parallelism)
- **Graphs** — severity distribution, status distribution charts

Các file JSON đó chứa trạng thái, bước, tệp đính kèm và nhãn của mỗi test. Allure CLI sau đó đọc các file JSON đó và tạo báo cáo HTML cuối cùng. Sự phân tách này có nghĩa là bạn có thể tái tạo HTML từ cùng các file kết quả bao nhiêu lần tùy thích — mà không cần chạy lại test.

**Tạo và xem báo cáo:**

```bash
# Bước 1: chạy test và ghi kết quả thô

# Bước 2a: phát triển — tạo HTML và tự động mở trình duyệt
allure serve allure-results
```

**Hệ thống phân cấp nhãn Allure — epic → feature → story:**

```
epic: "Blog API"
 └── feature: "Posts"
      ├── story: "Read"   — test_get_post, test_get_nonexistent_post
      └── story: "Create" — test_create_post
```

Ba nhãn này tạo thành chế độ xem "Behaviours" trong báo cáo Allure — một hệ thống phân cấp mà sản phẩm có thể đọc được. Khi bạn có 300 test trong suite lớn, danh sách tên test theo thứ tự bảng chữ cái gần như vô dụng để phân tích nguyên nhân gốc rễ. Hệ thống phân cấp cho phép bạn phát hiện rằng "User Authentication → Login → OAuth" có 3 lỗi trong một build trong khi "User Authentication → Login → Username-Password" không có — điều này ngay lập tức cho bạn biết việc triển khai OAuth bị lỗi, không phải toàn bộ luồng đăng nhập.

**Mức độ nghiêm trọng — và tại sao chúng ảnh hưởng đến phân loại:**

```python
allure.severity_level.BLOCKER   # hệ thống không thể sử dụng — deploy phải dừng
allure.severity_level.CRITICAL  # luồng nghiệp vụ cốt lõi bị hỏng — phải sửa hôm nay
allure.severity_level.NORMAL    # chức năng tiêu chuẩn bị suy giảm — sửa trong sprint
allure.severity_level.MINOR     # lỗi edge case — lên kế hoạch cho sprint tiếp theo
allure.severity_level.TRIVIAL   # thẩm mỹ hoặc không đáng kể — backlog
```

Mức độ nghiêm trọng không chỉ là trang trí. Trong CI, bạn có thể cấu hình pipeline chỉ fail build trên lỗi BLOCKER và CRITICAL. Nếu không có nhãn mức độ nghiêm trọng, mọi lỗi được xử lý như nhau — gây ra alert fatigue hoặc cấp bách giả.

**Tại sao `allure.step()` có giá trị hơn assertion thô để debug:**

Với `allure.step("Xác minh status là 201")`, báo cáo hiển thị "Bước 4 — Xác minh status là 201 — FAILED", và mọi bước trước đó hiển thị PASSED. Nhà phân tích ngay lập tức biết request đã được gửi (bước 2 passed), response đã được nhận (bước 3 passed), nhưng status sai (bước 4 failed). Việc thu hẹp lỗi xuống bước được đặt tên cụ thể loại bỏ hầu hết công việc thám tử.

**`allure.attach()` — lưu giữ bằng chứng cho phân tích sau sự cố:**

Đính kèm response body, ảnh chụp màn hình hoặc file log vào kết quả test có nghĩa là bạn có thể debug lỗi nhiều giờ hoặc nhiều ngày sau mà không cần chạy lại test. Đối với test thất bại không nhất quán (flaky test) điều này đặc biệt có giá trị.

```python
# tests/api/test_posts_allure.py
# Requirements: pip install allure-pytest requests jsonschema
# Run: pytest tests/api/test_posts_allure.py --alluredir=allure-results -v
# Then: allure serve allure-results

import allure
import pytest
import requests
from jsonschema import validate, ValidationError

BASE_URL = "https://jsonplaceholder.typicode.com"

POST_SCHEMA = {
    "type": "object",
    "required": ["id", "userId", "title", "body"],
    "properties": {
        "id":     {"type": "integer"},
        "userId": {"type": "integer"},
        "title":  {"type": "string"},
        "body":   {"type": "string"},
    },
}

COMMENT_SCHEMA = {
    "type": "object",
    "required": ["id", "postId", "name", "email", "body"],
    "properties": {
        "id":     {"type": "integer"},
        "postId": {"type": "integer"},
        "name":   {"type": "string"},
        "email":  {"type": "string"},
        "body":   {"type": "string"},
    },
}


@pytest.fixture(scope="session")
def session() -> requests.Session:
    """Shared HTTP session for the entire test run."""
    s = requests.Session()
    s.headers.update({"Content-Type": "application/json"})
    yield s
    s.close()


# ─────────────────────────────────────────────────────────────
# The @allure.epic / feature / story decorators define WHERE
# this test appears in the Behaviours tab of the Allure report.
# Without them every test is an orphan in the Suites view.
# ─────────────────────────────────────────────────────────────
@allure.epic("Blog API")
@allure.feature("Posts")
class TestPosts:

    @allure.story("Read")
    @allure.severity(allure.severity_level.CRITICAL)
    @allure.title("GET /posts/1 — should return 200 with valid schema")
    def test_get_post(self, session: requests.Session) -> None:
        with allure.step("Send GET /posts/1"):
            response = session.get(f"{BASE_URL}/posts/1")
            # Attaching the response body means anyone reading the report
            # later can see the exact payload — no need to re-run the test.
            allure.attach(
                response.text,
                name="Response Body",
                attachment_type=allure.attachment_type.JSON,
            )

        with allure.step("Assert status code is 200"):
            assert response.status_code == 200, (
                f"Expected 200, got {response.status_code}. Body: {response.text[:200]}"
            )

        with allure.step("Validate response against POST_SCHEMA"):
            try:
                validate(instance=response.json(), schema=POST_SCHEMA)
            except ValidationError as e:
                raise AssertionError(f"Schema validation failed: {e.message}") from e

    @allure.story("Create")
    @allure.severity(allure.severity_level.CRITICAL)
    @allure.title("POST /posts — should return 201 with a generated ID")
    def test_create_post(self, session: requests.Session) -> None:
        payload = {"title": "Allure Demo Post", "body": "Testing Allure annotations", "userId": 1}

        with allure.step(f"Send POST /posts with title='{payload['title']}'"):
            allure.attach(
                str(payload),
                name="Request Payload",
                attachment_type=allure.attachment_type.TEXT,
            )
            response = session.post(f"{BASE_URL}/posts", json=payload)

        with allure.step("Assert status code is 201"):
            assert response.status_code == 201, (
                f"Expected 201, got {response.status_code}. Body: {response.text[:200]}"
            )

        with allure.step("Assert response contains a generated ID"):
            created = response.json()
            allure.attach(
                str(created),
                name="Created Post Response",
                attachment_type=allure.attachment_type.TEXT,
            )
            assert "id" in created, f"Expected 'id' in response. Got keys: {list(created.keys())}"
            assert isinstance(created["id"], int), f"Expected id to be int, got {type(created['id'])}"

    @allure.story("Read")
    @allure.severity(allure.severity_level.NORMAL)
    @allure.title("GET /posts/99999 — non-existent post should return 404")
    def test_get_nonexistent_post(self, session: requests.Session) -> None:
        with allure.step("Send GET /posts/99999"):
            response = session.get(f"{BASE_URL}/posts/99999")

        with allure.step("Assert status code is 404"):
            assert response.status_code == 404, (
                f"Expected 404 for non-existent resource, got {response.status_code}"
            )

    @allure.story("Update")
    @allure.severity(allure.severity_level.NORMAL)
    @allure.title("PUT /posts/1 — should return 200 with updated fields")
    def test_update_post(self, session: requests.Session) -> None:
        payload = {"id": 1, "title": "Updated Title", "body": "Updated body", "userId": 1}

        with allure.step("Send PUT /posts/1 with updated payload"):
            response = session.put(f"{BASE_URL}/posts/1", json=payload)

        with allure.step("Assert status code is 200"):
            assert response.status_code == 200

        with allure.step("Assert updated fields are reflected in the response"):
            data = response.json()
            assert data.get("title") == "Updated Title", (
                f"Expected title 'Updated Title', got '{data.get('title')}'"
            )


@allure.epic("Blog API")
@allure.feature("Comments")
class TestComments:

    @allure.story("Read")
    @allure.severity(allure.severity_level.NORMAL)
    @allure.title("GET /posts/1/comments — should return list with valid schema")
    def test_get_comments_for_post(self, session: requests.Session) -> None:
        with allure.step("Send GET /posts/1/comments"):
            response = session.get(f"{BASE_URL}/posts/1/comments")
            allure.attach(
                response.text[:500],
                name="Response Body (first 500 chars)",
                attachment_type=allure.attachment_type.JSON,
            )

        with allure.step("Assert status code is 200"):
            assert response.status_code == 200

        with allure.step("Assert response is a non-empty list"):
            data = response.json()
            assert isinstance(data, list), f"Expected list, got {type(data)}"
            assert len(data) > 0, "Expected at least one comment"

        with allure.step("Validate first comment against COMMENT_SCHEMA"):
            try:
                validate(instance=data[0], schema=COMMENT_SCHEMA)
            except ValidationError as e:
                raise AssertionError(f"Comment schema failed: {e.message}") from e
```

```yaml
name: API Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install allure-pytest requests jsonschema

      - name: Install Allure CLI
        run: |
          wget -q https://github.com/allure-framework/allure2/releases/download/2.27.0/allure-2.27.0.tgz
          tar -xzf allure-2.27.0.tgz
          echo "$PWD/allure-2.27.0/bin" >> $GITHUB_PATH

      - name: Run tests
        run: pytest tests/ --alluredir=allure-results -v

      - name: Generate Allure HTML report
        if: always()   # run even if tests fail — you need the report most when tests fail
        run: allure generate allure-results -o allure-report --clean

      - name: Upload Allure report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: allure-report
          path: allure-report/
          retention-days: 14
```
