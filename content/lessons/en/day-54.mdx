## Intro

<En>
Today you add the Playwright UI layer to your capstone framework. This means wiring Playwright into the same project as your API tests, writing Page Objects for Sauce Demo (https://www.saucedemo.com), and making the UI tests run alongside the API tests in a single `pytest` command. By the end, one test run covers both API and UI — a professional, integrated test suite that matches how real QA teams work.

## Concept

<En>
**Why Page Objects exist — the real engineering reason:**

Imagine your app moves the login button from `button[name="Login"]` to `button[data-test="login-btn"]`. Without a Page Object, you grep through every test file to update every reference. With a Page Object, you change one line in `LoginPage.__init__` and every test that uses `LoginPage` is instantly fixed.

This is not just about cleanliness. It is about **maintenance cost**. A team running 200 UI tests against a product that ships weekly cannot afford to spend two hours updating locators every sprint. The Page Object pattern concentrates locator knowledge into one place — the page class — so that structural changes in the UI require only structural changes in the page class, not in the tests.

**Why locators live in `__init__` — lazy evaluation explained:**

When you write `self._username = page.get_by_placeholder("Username")` in `__init__`, you are NOT querying the DOM. Playwright locators are descriptions, not live DOM nodes. The actual DOM query happens only when you call an action: `.fill()`, `.click()`, `.text_content()`. This means:

1. The locator object is cheap to create — no network round-trip, no browser call.
2. The element does not need to exist when `LoginPage(page)` is constructed. It only needs to exist when `.fill()` is called.
3. Locators automatically retry on each action (up to the timeout). You never call `.wait_for_element()` before every interaction.

**Why `BasePage` centralizes navigation:**

If the base URL ever changes — from `https://www.saucedemo.com` to a staging URL like `https://staging.saucedemo.com` — you change one string in `BasePage.navigate()`. Every page class that calls `self.navigate("/inventory.html")` picks up the new URL automatically. This is the DRY principle applied to test infrastructure: the base URL is information that belongs in one place.

**How the screenshot-on-failure fixture works:**

The fixture uses two pytest mechanisms together:

1. `@pytest.hookimpl(hookwrapper=True)` — This decorator makes `pytest_runtest_makereport` a hook wrapper. pytest calls it at each phase of the test lifecycle (setup, call, teardown). We store the result object on the test item with `setattr(item, "rep_call", rep)`.

2. `autouse=True` fixture that `yield`s — After the test body runs, control returns to the fixture. At that point `request.node.rep_call` exists on the item (because the hook ran first). If `rep_call.failed` is `True`, we call `page.screenshot()` and attach the bytes to Allure.

The result: every failing UI test automatically gets a browser screenshot attached to its Allure report entry — visual evidence of exactly what the browser showed at the moment of failure, with zero boilerplate in the test itself.

**How conftest.py scoping keeps browser fixtures out of API tests:**

`pytest-playwright` provides `browser`, `browser_context`, and `page` fixtures. If you put them in the root `conftest.py` with `autouse=True`, every test — including your fast API tests — would spin up a browser. That would slow the suite dramatically.

The solution is scoping:

```
tests/
├── conftest.py          # shared: api_client, auth headers, screenshot hook
├── api/
│   └── conftest.py      # (empty or API-only fixtures)
└── ui/
    └── conftest.py      # browser_context, page overrides for UI-only fixtures
```

Fixtures defined in `tests/ui/conftest.py` are only available to tests collected from `tests/ui/`. API tests in `tests/api/` never see the `page` fixture. `pytest-playwright`'s built-in `page` fixture is only activated when a test actually requests it, so API tests are not affected even if `pytest-playwright` is installed globally.

**Why Sauce Demo:**

- Publicly available, always up, no account required
- Designed specifically for automation practice
- Has login, inventory, cart, and checkout flows covering real user scenarios
- Standard credentials: `standard_user` / `secret_sauce`
- Includes intentionally broken user accounts (`locked_out_user`, `error_user`) for negative testing


**Tại sao Page Object tồn tại — lý do kỹ thuật thực sự:**

Hãy tưởng tượng app của bạn di chuyển nút đăng nhập từ `button[name="Login"]` sang `button[data-test="login-btn"]`. Nếu không có Page Object, bạn phải grep qua mọi file test để cập nhật từng tham chiếu. Với Page Object, bạn chỉ đổi một dòng trong `LoginPage.__init__` và mọi test dùng `LoginPage` được sửa ngay lập tức.

Đây không chỉ là về sự gọn gàng. Đây là về **chi phí bảo trì**. Một team chạy 200 UI test trên sản phẩm ship hàng tuần không thể dành hai tiếng cập nhật locator mỗi sprint. Pattern Page Object tập trung kiến thức locator vào một nơi — lớp page — để thay đổi cấu trúc UI chỉ yêu cầu thay đổi cấu trúc trong lớp page, không phải trong các test.

**Tại sao locator nằm trong `__init__` — giải thích lazy evaluation:**

Khi bạn viết `self._username = page.get_by_placeholder("Username")` trong `__init__`, bạn KHÔNG query DOM. Playwright locator là mô tả, không phải DOM node trực tiếp. Query DOM thực sự chỉ xảy ra khi bạn gọi action: `.fill()`, `.click()`, `.text_content()`. Điều này có nghĩa là:

1. Đối tượng locator rẻ để tạo — không có network round-trip, không có browser call.
2. Phần tử không cần tồn tại khi `LoginPage(page)` được tạo. Nó chỉ cần tồn tại khi `.fill()` được gọi.
3. Locator tự động retry mỗi action (đến timeout). Bạn không bao giờ phải gọi `.wait_for_element()` trước mỗi tương tác.

**Tại sao `BasePage` tập trung navigation:**

Nếu base URL thay đổi — từ `https://www.saucedemo.com` sang URL staging như `https://staging.saucedemo.com` — bạn chỉ đổi một chuỗi trong `BasePage.navigate()`. Mọi lớp page gọi `self.navigate("/inventory.html")` tự động dùng URL mới. Đây là nguyên tắc DRY áp dụng cho test infrastructure: base URL là thông tin thuộc về một nơi.

**Screenshot-on-failure fixture hoạt động như thế nào:**

Fixture dùng hai cơ chế pytest kết hợp:

1. `@pytest.hookimpl(hookwrapper=True)` — Decorator này biến `pytest_runtest_makereport` thành hook wrapper. pytest gọi nó ở mỗi phase của test lifecycle (setup, call, teardown). Chúng ta lưu kết quả trên test item bằng `setattr(item, "rep_call", rep)`.

2. Fixture `autouse=True` có `yield` — Sau khi thân test chạy, control trả về fixture. Lúc đó `request.node.rep_call` tồn tại trên item. Nếu `rep_call.failed` là `True`, chúng ta gọi `page.screenshot()` và đính kèm bytes vào Allure.

Kết quả: mọi UI test thất bại tự động có screenshot browser đính kèm vào Allure report — bằng chứng trực quan về những gì browser hiển thị đúng vào lúc thất bại, không cần boilerplate trong test.

## Code / Demo

<En>

**Part 1 — BasePage: the navigation foundation**

`BasePage` owns the one piece of configuration that all page classes share: the base URL. Every page class inherits from it and calls `self.navigate("/some-path")` rather than hardcoding the full URL. When the URL changes, only `BasePage` needs updating.

</En>
<Vi>

**Phần 1 — BasePage: nền tảng navigation**

`BasePage` sở hữu phần cấu hình duy nhất mà tất cả lớp page chia sẻ: base URL. Mọi lớp page kế thừa từ nó và gọi `self.navigate("/some-path")` thay vì hardcode URL đầy đủ. Khi URL thay đổi, chỉ `BasePage` cần cập nhật.

</Vi>

```python
# pages/base_page.py
from playwright.sync_api import Page, expect

BASE_URL = "https://www.saucedemo.com"


class BasePage:
    """Shared foundation for all Sauce Demo page objects.

    Centralises the base URL so every subclass calls self.navigate("/path")
    rather than hardcoding the full URL. One change here updates all pages.
    """

    def __init__(self, page: Page) -> None:
        self.page = page

    def navigate(self, path: str = "") -> None:
        """Navigate to BASE_URL + path.

        Examples:
            self.navigate("/")               → https://www.saucedemo.com/
            self.navigate("/inventory.html") → https://www.saucedemo.com/inventory.html
        """
        self.page.goto(f"{BASE_URL}{path}")

    def assert_url_contains(self, fragment: str) -> None:
        """Assert the current URL contains the given fragment.

        Uses Playwright's built-in assertion with automatic retry so you
        do not need an explicit wait before calling this.
        """
        expect(self.page).to_have_url(lambda url: fragment in url)

    def get_title(self) -> str:
        """Return the current page <title>."""
        return self.page.title()
```

<En>

**Part 2 — LoginPage: locators and actions**

`LoginPage` stores all locators in `__init__` (lazy — no DOM queries yet) and exposes clean action methods. The test never touches raw Playwright calls — it speaks the language of the product (`login()`, `assert_error_visible()`).

</En>
<Vi>

**Phần 2 — LoginPage: locator và action**

`LoginPage` lưu tất cả locator trong `__init__` (lazy — chưa có DOM query) và công khai các phương thức action rõ ràng. Test không bao giờ chạm vào Playwright call trực tiếp — nó nói ngôn ngữ của sản phẩm (`login()`, `assert_error_visible()`).

</Vi>

```python
# pages/login_page.py
from playwright.sync_api import Page, expect
from pages.base_page import BasePage


class LoginPage(BasePage):
    """Page Object for the Sauce Demo login screen.

    All locators are stored as instance attributes in __init__.
    No DOM query happens here — Playwright locators are lazy descriptors.
    The query runs only when an action method calls .fill() or .click().
    """

    def __init__(self, page: Page) -> None:
        super().__init__(page)
        # Role-based and accessible locators are preferred over CSS selectors.
        # They stay valid even when the CSS class names are refactored.
        self._username = page.get_by_placeholder("Username")
        self._password = page.get_by_placeholder("Password")
        self._login_btn = page.get_by_role("button", name="Login")
        # data-test attributes are the most stable locator strategy —
        # QA teams negotiate with dev to add them to testable elements.
        self._error_msg = page.locator("[data-test='error']")

    def open(self) -> None:
        """Navigate to the login page."""
        self.navigate("/")

    def login(self, username: str, password: str) -> None:
        """Fill in credentials and submit the login form.

        Does NOT assert the outcome — the test decides what to check.
        A helper that only does one thing is easier to reuse in different
        test scenarios (success, wrong password, locked-out user).
        """
        self._username.fill(username)
        self._password.fill(password)
        self._login_btn.click()

    def assert_error_visible(self, message: str) -> None:
        """Assert the login error banner is visible and contains the given text.

        Uses Playwright's built-in expect() which auto-retries for up to
        the configured timeout (default 30 s). No explicit sleep needed.
        """
        expect(self._error_msg).to_be_visible()
        expect(self._error_msg).to_contain_text(message)

    def assert_login_btn_visible(self) -> None:
        """Assert the login button is present — useful as a page-load check."""
        expect(self._login_btn).to_be_visible()
```

<En>

**Part 3 — InventoryPage: state and interactions**

`InventoryPage` encapsulates everything about the product list page — how to confirm it loaded, how to add items, and how to read the cart badge count. The cart count method handles the case where the badge is absent (zero items) defensively.

</En>
<Vi>

**Phần 3 — InventoryPage: trạng thái và tương tác**

`InventoryPage` đóng gói mọi thứ về trang danh sách sản phẩm — cách xác nhận nó đã load, cách thêm item, và cách đọc số lượng huy hiệu giỏ hàng. Phương thức đếm giỏ hàng xử lý phòng thủ trường hợp huy hiệu vắng mặt (không có item).

</Vi>

```python
# pages/inventory_page.py
from playwright.sync_api import Page, expect
from pages.base_page import BasePage

INVENTORY_URL = "https://www.saucedemo.com/inventory.html"


class InventoryPage(BasePage):
    """Page Object for the Sauce Demo inventory (product listing) page."""

    def __init__(self, page: Page) -> None:
        super().__init__(page)
        # .inventory_item matches every product card on the page.
        self._items = page.locator(".inventory_item")
        # The cart badge only exists in the DOM when at least one item is in cart.
        self._cart_badge = page.locator(".shopping_cart_badge")
        self._cart_icon = page.locator(".shopping_cart_link")

    def assert_loaded(self) -> None:
        """Assert the inventory page has fully loaded.

        Checks both the URL (confirming navigation succeeded) and that
        at least one product card is visible (confirming data loaded).
        """
        expect(self.page).to_have_url(INVENTORY_URL)
        expect(self._items.first).to_be_visible()

    def item_count(self) -> int:
        """Return the number of product cards on the page."""
        return self._items.count()

    def add_first_item_to_cart(self) -> None:
        """Click the 'Add to cart' button on the first listed product."""
        self._items.first.get_by_role("button", name="Add to cart").click()

    def add_item_by_name(self, name: str) -> None:
        """Click 'Add to cart' for the product with the given name.

        Useful for deterministic tests that must add a specific product
        rather than whichever happens to be listed first.
        """
        item = self._items.filter(has_text=name)
        item.get_by_role("button", name="Add to cart").click()

    def cart_count(self) -> int:
        """Return the number shown on the cart badge, or 0 if badge is absent.

        The cart badge element only exists in the DOM when at least one item
        has been added. Checking .count() == 0 first avoids a timeout error
        from calling .text_content() on a non-existent element.
        """
        if self._cart_badge.count() == 0:
            return 0
        return int(self._cart_badge.text_content() or "0")

    def go_to_cart(self) -> None:
        """Click the cart icon to navigate to the cart page."""
        self._cart_icon.click()
```

**Phần 4 — test_login.py: file test đầy đủ với Allure annotation**

Test nói ngôn ngữ sản phẩm, không phải ngôn ngữ Playwright. Mỗi bước được bọc trong `allure.step()` để Allure report hiển thị tường thuật dễ đọc của con người về những gì đã xảy ra. Lưu ý thân test rất gọn — mọi chi tiết locator được ẩn trong page object.

```python
# tests/ui/test_login.py
import allure
import pytest
from playwright.sync_api import Page

from pages.login_page import LoginPage
from pages.inventory_page import InventoryPage

VALID_USER = "standard_user"
VALID_PASS = "secret_sauce"


@allure.epic("Sauce Demo UI")
@allure.feature("Login")
class TestLogin:
    """UI test suite for the Sauce Demo login flow.

    Uses Page Object Model so tests never reference raw Playwright locators.
    Run with: pytest tests/ui/ -v --headed
    """

    @allure.story("Happy path")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.ui
    def test_login_success(self, page: Page) -> None:
        """Valid credentials should navigate to the inventory page."""
        login = LoginPage(page)
        inventory = InventoryPage(page)

        with allure.step("Open the Sauce Demo login page"):
            login.open()
            login.assert_login_btn_visible()

        with allure.step("Enter valid credentials and submit"):
            login.login(VALID_USER, VALID_PASS)

        with allure.step("Verify the inventory page has loaded"):
            inventory.assert_loaded()

    @allure.story("Negative")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.ui
    def test_login_wrong_password(self, page: Page) -> None:
        """Wrong password should display an inline error message."""
        login = LoginPage(page)

        with allure.step("Open the login page"):
            login.open()

        with allure.step("Submit with correct username but wrong password"):
            login.login(VALID_USER, "wrongpassword")

        with allure.step("Assert error message is visible with expected text"):
            login.assert_error_visible("Username and password do not match")

    @allure.story("Negative")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.ui
    def test_login_locked_out_user(self, page: Page) -> None:
        """Locked-out user should see the locked-out error message."""
        login = LoginPage(page)

        with allure.step("Open the login page"):
            login.open()

        with allure.step("Submit with locked_out_user credentials"):
            login.login("locked_out_user", VALID_PASS)

        with allure.step("Assert locked-out error is shown"):
            login.assert_error_visible("Sorry, this user has been locked out")

    @allure.story("Happy path")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.ui
    def test_add_item_to_cart(self, page: Page) -> None:
        """After login, adding the first item should update the cart badge to 1."""
        login = LoginPage(page)
        inventory = InventoryPage(page)

        with allure.step("Log in with valid credentials"):
            login.open()
            login.login(VALID_USER, VALID_PASS)
            inventory.assert_loaded()

        with allure.step("Add the first listed item to the cart"):
            inventory.add_first_item_to_cart()

        with allure.step("Verify the cart badge shows exactly 1"):
            assert inventory.cart_count() == 1, (
                f"Expected cart count 1, got {inventory.cart_count()}"
            )

    @allure.story("Happy path")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.ui
    def test_cart_page_navigation(self, page: Page) -> None:
        """Clicking the cart icon should navigate to /cart.html."""
        login = LoginPage(page)
        inventory = InventoryPage(page)

        with allure.step("Log in and verify inventory loaded"):
            login.open()
            login.login(VALID_USER, VALID_PASS)
            inventory.assert_loaded()

        with allure.step("Add item then click the cart icon"):
            inventory.add_first_item_to_cart()
            inventory.go_to_cart()

        with allure.step("Assert URL is the cart page"):
            inventory.assert_url_contains("/cart.html")
```

**Part 5 — conftest.py: the screenshot-on-failure fixture**

This fixture hooks into pytest's test lifecycle. The `hookimpl` stores the test result at the `call` phase on the item itself. The `autouse` fixture then reads it after `yield` — if the test failed, it captures a screenshot and attaches it to Allure. Zero boilerplate in each test.

</En>
<Vi>

**Phần 5 — conftest.py: fixture screenshot khi thất bại**

Fixture này hook vào test lifecycle của pytest. `hookimpl` lưu kết quả test ở phase `call` trên chính item. Fixture `autouse` sau đó đọc nó sau `yield` — nếu test thất bại, nó chụp screenshot và đính kèm vào Allure. Không cần boilerplate trong mỗi test.

</Vi>

```python
# tests/conftest.py
import pytest
import allure
from playwright.sync_api import Page


# ---------------------------------------------------------------------------
# Hook: store test phase results on the item so fixtures can inspect them
# ---------------------------------------------------------------------------

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    """Store the test outcome at each phase on the test item.

    pytest calls this hook three times per test: setup, call, teardown.
    We capture the 'call' result (the actual test body) so that the
    screenshot fixture below can check whether the test body failed.

    Without this hook, request.node.rep_call would not exist and the
    screenshot fixture could not know the test outcome.
    """
    outcome = yield
    rep = outcome.get_result()
    # Store rep_setup, rep_call, or rep_teardown depending on the phase.
    setattr(item, f"rep_{rep.when}", rep)


# ---------------------------------------------------------------------------
# Fixture: automatically attach a screenshot to Allure on UI test failure
# ---------------------------------------------------------------------------

@pytest.fixture(autouse=True)
def screenshot_on_failure(page: Page, request: pytest.FixtureRequest):
    """Capture and attach a browser screenshot when a UI test fails.

    autouse=True means this fixture applies to every test that has a
    'page' fixture in scope — effectively all UI tests.

    How it works:
    1. yield → the test body runs
    2. After yield → check if rep_call exists and was a failure
    3. If failed → call page.screenshot() and attach the PNG bytes to Allure

    The result appears in the Allure report under Attachments for the
    failed test, giving you a visual snapshot of the browser state at
    the exact moment the assertion failed.
    """
    yield
    # rep_call is set by pytest_runtest_makereport above.
    # hasattr guard handles setup failures where rep_call never reaches 'call'.
    rep_call = getattr(request.node, "rep_call", None)
    if rep_call is not None and rep_call.failed:
        screenshot_bytes = page.screenshot(full_page=True)
        allure.attach(
            screenshot_bytes,
            name="failure_screenshot",
            attachment_type=allure.attachment_type.PNG,
        )
```
