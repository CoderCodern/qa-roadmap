## Intro

<En>
Most QA beginners only test the happy path — valid inputs that work correctly. But the most valuable tests are the ones that break things: invalid inputs, missing fields, boundary values, malformed JSON. Negative testing verifies that the API fails gracefully with the right error response instead of crashing or exposing sensitive information.
</En>
<Vi>
Hầu hết người mới bắt đầu QA chỉ kiểm tra happy path — các đầu vào hợp lệ hoạt động đúng. Nhưng các test có giá trị nhất là những test phá vỡ mọi thứ: đầu vào không hợp lệ, thiếu trường, giá trị biên, JSON sai định dạng. Kiểm thử tiêu cực xác minh rằng API thất bại một cách duyên dáng với response lỗi đúng thay vì crash hoặc lộ thông tin nhạy cảm.
</Vi>

## Concept

<En>
**The 4 dimensions of negative API testing:**

**1. Invalid input values:**
- Wrong data type (string where int expected)
- Value outside allowed range (age = -5, age = 999)
- Invalid format (email without @, non-UUID where UUID expected)
- Empty string where content required

**2. Missing required fields:**
- Omit each required field, one at a time — this isolates which validation message appears
- Expect 400 or 422 with a meaningful error message pointing to the specific missing field
- Never omit all fields at once: that tests only one scenario and hides individual validation gaps

**3. Boundary Value Analysis (BVA) applied to APIs:**
Boundary Value Analysis is a technique where you test the exact edges of valid input ranges, because bugs most commonly appear at boundaries:
- Min-1, Min, Max, Max+1
- Example for a username that accepts 3–20 characters:
  - Length 2 → expect 422 (below minimum)
  - Length 3 → expect 201 (minimum valid)
  - Length 20 → expect 201 (maximum valid)
  - Length 21 → expect 422 (above maximum)

**4. Security edge cases:**
- SQL injection in string fields: `'; DROP TABLE users; --`
- XSS payload in text fields: `<script>alert(1)</script>`
- Extremely long strings (buffer overflow attempts)
- Unexpected content types (send XML to JSON endpoint)

**What good error responses look like:**
```json
{
  "error": "Validation failed",
  "details": [
    {"field": "email", "message": "Must be a valid email address"},
    {"field": "age", "message": "Must be between 0 and 150"}
  ]
}
```

**What to assert in negative tests:**
- Status code is 4xx — not 5xx (500 means the server crashed on your input, which is a bug)
- Response body contains an `error` or `message` field
- Error message describes the problem without leaking internals
- No stack traces, database names, table names, or raw SQL in the response

**400 vs 422:**
- 400 Bad Request — request is syntactically malformed (e.g. invalid JSON, missing Content-Type)
- 422 Unprocessable Entity — request is well-formed but fails semantic validation (e.g. email field present but not a valid email)
Both are acceptable for validation failures; the important thing is consistency across your API.
</En>
<Vi>
**4 chiều của kiểm thử API tiêu cực:**

**1. Giá trị đầu vào không hợp lệ:**
- Sai kiểu dữ liệu (chuỗi ở nơi mong đợi int)
- Giá trị ngoài phạm vi được phép (age = -5, age = 999)
- Định dạng không hợp lệ (email không có @)
- Chuỗi rỗng ở nơi yêu cầu nội dung

**2. Thiếu trường bắt buộc:**
- Bỏ qua từng trường bắt buộc, một lần một cái — điều này cô lập thông báo xác thực nào xuất hiện
- Mong đợi 400 hoặc 422 với thông báo lỗi có ý nghĩa chỉ đến trường cụ thể bị thiếu
- Không bao giờ bỏ qua tất cả trường cùng một lúc: điều đó chỉ kiểm thử một kịch bản và ẩn các khoảng trống xác thực riêng lẻ

**3. Phân tích giá trị biên (BVA) áp dụng cho API:**
Phân tích giá trị biên là kỹ thuật kiểm thử các cạnh chính xác của phạm vi đầu vào hợp lệ, vì lỗi thường xuất hiện nhất tại các biên:
- Min-1, Min, Max, Max+1
- Ví dụ cho username chấp nhận 3–20 ký tự:
  - Độ dài 2 → mong đợi 422 (dưới tối thiểu)
  - Độ dài 3 → mong đợi 201 (tối thiểu hợp lệ)
  - Độ dài 20 → mong đợi 201 (tối đa hợp lệ)
  - Độ dài 21 → mong đợi 422 (trên tối đa)

**4. Edge case bảo mật:**
- SQL injection trong trường chuỗi: `'; DROP TABLE users; --`
- XSS payload trong trường văn bản: `<script>alert(1)</script>`
- Chuỗi cực dài (thử tràn bộ đệm)
- Content type không mong đợi (gửi XML đến endpoint JSON)

**Response lỗi tốt trông như thế nào:**
```json
{
  "error": "Validation failed",
  "details": [
    {"field": "email", "message": "Must be a valid email address"},
    {"field": "age", "message": "Must be between 0 and 150"}
  ]
}
```

**Những gì cần assert trong negative test:**
- Status code là 4xx — không phải 5xx (500 nghĩa là server crash với đầu vào của bạn, đó là bug)
- Body chứa trường `error` hoặc `message`
- Thông báo lỗi mô tả vấn đề mà không lộ nội bộ
- Không có stack trace, tên database, tên table, hay SQL thô trong response

**400 vs 422:**
- 400 Bad Request — request sai cú pháp (ví dụ JSON không hợp lệ, thiếu Content-Type)
- 422 Unprocessable Entity — request được định dạng tốt nhưng thất bại xác thực ngữ nghĩa (ví dụ trường email có nhưng không phải email hợp lệ)
Cả hai đều chấp nhận được cho lỗi xác thực; điều quan trọng là tính nhất quán trên toàn bộ API của bạn.
</Vi>

```python
import requests
import pytest

BASE_URL = "https://jsonplaceholder.typicode.com"

# Note: JSONPlaceholder is lenient (it accepts almost anything),
# so we use it to demonstrate patterns with adjusted expectations.
# In a real API with strict validation, the status code assertions change to 400/422.

def test_get_nonexistent_resource():
    """404 for a resource that does not exist."""
    response = requests.get(f"{BASE_URL}/posts/99999")
    assert response.status_code == 404

def test_invalid_resource_id_type():
    """String id where integer expected — many APIs return 400 or 404."""
    response = requests.get(f"{BASE_URL}/posts/not-an-id")
    assert response.status_code in (400, 404), \
        f"Expected 400 or 404 for invalid ID, got {response.status_code}"

@pytest.mark.parametrize("field,value,description", [
    ("email",    "notanemail",   "invalid email format"),
    ("age",      -1,             "negative age"),
    ("username", "",             "empty username"),
    ("role",     "superadmin",   "invalid role value"),
])
def test_invalid_field_values(field, value, description):
    """400 or 422 for invalid field values in a real validated API."""
    payload = {field: value}
    response = requests.post(f"{BASE_URL}/posts", json=payload)
    # JSONPlaceholder returns 201 for everything.
    # In a real API: assert response.status_code in (400, 422)
    print(f"  {description}: sent {field}={value!r}, got {response.status_code}")
    assert response.status_code != 500, "Server must not crash on invalid input"
```

```python
@pytest.mark.parametrize("payload,missing_field", [
    ({"body": "content", "userId": 1}, "title"),
    ({"title": "Test",   "userId": 1}, "body"),
    ({"title": "Test",   "body": "x"}, "userId"),
])
def test_missing_required_field(payload, missing_field):
    """
    Test each required field missing separately.
    This is important: testing all missing at once only tells you
    'the API rejected it' — not which field caused the failure.
    """
    response = requests.post(f"{BASE_URL}/posts", json=payload)
    print(f"  Missing '{missing_field}': status {response.status_code}")
    # In a real validated API:
    # assert response.status_code in (400, 422)
    # assert missing_field in response.json().get("details", [{}])[0].get("field", "")

def test_empty_body():
    """POST with completely empty body should not cause a 500."""
    response = requests.post(f"{BASE_URL}/posts", json={})
    assert response.status_code != 500, "Server must handle empty body gracefully"
    print(f"Empty body response: {response.status_code}")
```

**Phần 3 — Phân tích giá trị biên và edge case bảo mật**

```python
@pytest.mark.parametrize("length,expected_status", [
    (2,  422),   # below minimum (min is 3)
    (3,  201),   # at minimum — valid
    (20, 201),   # at maximum — valid
    (21, 422),   # above maximum (max is 20)
])
def test_username_boundary_values(length, expected_status):
    """BVA: test the edges of the accepted username length range (3-20 chars)."""
    username = "a" * length
    response = requests.post(f"{BASE_URL}/users",
                             json={"username": username, "email": "x@example.com"})
    # JSONPlaceholder doesn't enforce this — in a real API:
    # assert response.status_code == expected_status, \
    #     f"username length={length}: expected {expected_status}, got {response.status_code}"
    print(f"  username length={length}: status={response.status_code} (expected {expected_status})")

def test_sql_injection_payload():
    """SQL injection input must not cause a 500 or return DB error text."""
    sql_payload = "'; DROP TABLE users; --"
    response = requests.post(f"{BASE_URL}/posts",
                             json={"title": sql_payload, "body": "x", "userId": 1})
    assert response.status_code != 500, "Server must not crash on SQL injection input"
    body_text = response.text.lower()
    for leak in ("syntax error", "sqlite", "mysql", "postgresql", "pg_"):
        assert leak not in body_text, f"Response leaks DB error text: '{leak}'"
    print(f"SQL injection: status {response.status_code} — no DB error text leaked")

def test_very_long_string():
    """Extremely long field value must not crash the server."""
    long_title = "A" * 10_000
    response = requests.post(f"{BASE_URL}/posts",
                             json={"title": long_title, "body": "x", "userId": 1})
    assert response.status_code != 500, "Server must not crash on 10k-char input"
    print(f"Very long title: status {response.status_code}")
```
