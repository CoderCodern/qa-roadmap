## Intro

<En>
API testing is the skill that separates junior QA engineers from mid-level ones. It's faster than UI testing, closer to the system's actual behaviour, and catches bugs that the UI might hide. But before you can test APIs, you need to understand HTTP — the protocol that powers every API request and response on the web.
</En>
<Vi>
Kiểm thử API là kỹ năng phân biệt kỹ sư QA cấp junior với mid-level. Nó nhanh hơn kiểm thử UI, gần hơn với hành vi thực tế của hệ thống và bắt được các lỗi mà UI có thể ẩn giấu. Nhưng trước khi bạn có thể kiểm thử API, bạn cần hiểu HTTP — giao thức cung cấp sức mạnh cho mọi API request và response trên web.
</Vi>

## Concept

<En>
**HTTP request structure:**

Every HTTP request has four parts. As a QA engineer you must know what belongs in each one:

| Part | Description | Example |
|------|-------------|---------|
| **Method** | The verb — what action to perform | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |
| **URL** | The target endpoint (resource + path) | `https://api.example.com/users/42` |
| **Headers** | Key-value metadata about the request | `Content-Type: application/json`, `Authorization: Bearer <token>` |
| **Body** | Data payload sent with the request | `{"email": "alice@example.com"}` — only for POST/PUT/PATCH |

**HTTP response structure:**

The server always replies with three parts:

| Part | Description | Example |
|------|-------------|---------|
| **Status code** | Numeric result — tells you what happened | `200`, `404`, `500` |
| **Headers** | Metadata from the server | `Content-Type: application/json`, `Set-Cookie` |
| **Body** | The returned data | JSON object, HTML page, or empty |

**The most important status codes for API testing:**

| Code | Meaning | When you see it in the wild |
|------|---------|---------------------------|
| 200 | OK | Successful GET, PUT, PATCH — generic success |
| 201 | Created | POST that successfully created a resource |
| 204 | No Content | DELETE or PATCH that succeeds but returns no body |
| 400 | Bad Request | The client sent malformed input the server refuses to process |
| 401 | Unauthorized | Missing or invalid authentication token |
| 403 | Forbidden | Authenticated but the user lacks permission |
| 404 | Not Found | The resource doesn't exist at that URL |
| 409 | Conflict | Duplicate resource (e.g., email already registered) |
| 422 | Unprocessable Entity | Input parsed correctly but fails validation rules |
| 429 | Too Many Requests | Rate limit hit |
| 500 | Internal Server Error | Bug or crash on the server side |
| 503 | Service Unavailable | Server is overloaded or down for maintenance |

**HTTP methods — semantics and idempotency:**

Idempotent means calling the same request multiple times produces the same result as calling it once. This matters for retry logic and test design.

| Method | Purpose | Idempotent? | Has Body? | Safe? |
|--------|---------|-------------|-----------|-------|
| GET | Read a resource | Yes | No | Yes |
| POST | Create a new resource | No | Yes | No |
| PUT | Replace a resource entirely | Yes | Yes | No |
| PATCH | Partially update a resource | Usually | Yes | No |
| DELETE | Remove a resource | Yes | Optional | No |
| OPTIONS | Discover allowed methods | Yes | No | Yes |

A "safe" method does not modify server state. GET and OPTIONS are read-only by definition.

**PATCH vs PUT — when to use which:**

- Use **PUT** when you are sending the complete replacement object. Missing fields get overwritten with defaults or nulls.
- Use **PATCH** when you are sending only the fields you want to change. Other fields remain untouched.

A common bug to test: `PUT /users/42` called with a partial body silently clears fields not included. Always test that PUT includes all required fields.

**What the Content-Type header does:**

`Content-Type: application/json` tells the server how to parse the request body. If you send JSON but forget this header, many servers return `400 Bad Request` because they don't know how to read the body. When testing APIs, always verify the correct Content-Type is set in both the request and the response.

**401 vs 403 — the most commonly confused pair:**

- **401 Unauthorized**: The server doesn't know who you are. You either sent no token, an expired token, or a malformed token. Fix: log in and get a fresh token.
- **403 Forbidden**: The server knows exactly who you are, but you don't have permission to perform this action. Fix: your account needs elevated privileges.

Testing tip: always test both 401 (no token) and 403 (wrong role) as separate negative test cases.
</En>
<Vi>
**Cấu trúc HTTP request:**

Mỗi HTTP request có bốn phần. Là kỹ sư QA, bạn cần biết từng phần chứa gì:

| Phần | Mô tả | Ví dụ |
|------|-------|-------|
| **Method** | Động từ — hành động cần thực hiện | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |
| **URL** | Endpoint mục tiêu (tài nguyên + đường dẫn) | `https://api.example.com/users/42` |
| **Headers** | Metadata dạng key-value về request | `Content-Type: application/json`, `Authorization: Bearer <token>` |
| **Body** | Dữ liệu gửi kèm request | `{"email": "alice@example.com"}` — chỉ dùng với POST/PUT/PATCH |

**Cấu trúc HTTP response:**

Server luôn trả lời với ba phần:

| Phần | Mô tả | Ví dụ |
|------|-------|-------|
| **Status code** | Kết quả dạng số — cho biết điều gì xảy ra | `200`, `404`, `500` |
| **Headers** | Metadata từ server | `Content-Type: application/json`, `Set-Cookie` |
| **Body** | Dữ liệu được trả về | JSON object, trang HTML, hoặc rỗng |

**Các status code quan trọng nhất cho kiểm thử API:**

| Code | Ý nghĩa | Khi nào gặp trong thực tế |
|------|---------|--------------------------|
| 200 | OK | GET, PUT, PATCH thành công — thành công thông thường |
| 201 | Created | POST tạo tài nguyên thành công |
| 204 | No Content | DELETE hoặc PATCH thành công nhưng không trả body |
| 400 | Bad Request | Client gửi dữ liệu sai định dạng |
| 401 | Unauthorized | Token xác thực thiếu hoặc không hợp lệ |
| 403 | Forbidden | Đã xác thực nhưng không có quyền |
| 404 | Not Found | Tài nguyên không tồn tại tại URL đó |
| 409 | Conflict | Tài nguyên trùng lặp (email đã đăng ký) |
| 422 | Unprocessable Entity | Dữ liệu hợp lệ về cú pháp nhưng không qua validation |
| 429 | Too Many Requests | Vượt giới hạn tốc độ |
| 500 | Internal Server Error | Lỗi hoặc crash phía server |
| 503 | Service Unavailable | Server quá tải hoặc bảo trì |

**HTTP method — ngữ nghĩa và tính idempotent:**

Idempotent có nghĩa là gọi cùng một request nhiều lần cho kết quả giống như gọi một lần. Điều này quan trọng cho logic retry và thiết kế test.

| Method | Mục đích | Idempotent? | Có Body? | An toàn? |
|--------|---------|-------------|----------|---------|
| GET | Đọc tài nguyên | Có | Không | Có |
| POST | Tạo tài nguyên mới | Không | Có | Không |
| PUT | Thay thế toàn bộ tài nguyên | Có | Có | Không |
| PATCH | Cập nhật một phần tài nguyên | Thường | Có | Không |
| DELETE | Xoá tài nguyên | Có | Tuỳ chọn | Không |
| OPTIONS | Khám phá method được phép | Có | Không | Có |

Method "an toàn" là method không thay đổi trạng thái server. GET và OPTIONS chỉ đọc theo định nghĩa.

**PATCH vs PUT — khi nào dùng cái nào:**

- Dùng **PUT** khi bạn gửi toàn bộ object thay thế. Các trường thiếu sẽ bị ghi đè bằng giá trị mặc định hoặc null.
- Dùng **PATCH** khi bạn chỉ gửi các trường muốn thay đổi. Các trường còn lại giữ nguyên.

Lỗi thường gặp cần kiểm thử: `PUT /users/42` gọi với body thiếu trường sẽ âm thầm xoá trắng các trường đó. Luôn kiểm tra PUT có đủ các trường bắt buộc.

**Header Content-Type làm gì:**

`Content-Type: application/json` báo cho server biết cách phân tích body request. Nếu bạn gửi JSON nhưng quên header này, nhiều server trả về `400 Bad Request`. Khi kiểm thử API, luôn xác minh Content-Type đúng cho cả request lẫn response.

**401 vs 403 — cặp hay bị nhầm nhất:**

- **401 Unauthorized**: Server không biết bạn là ai. Bạn không gửi token, token hết hạn, hoặc token sai định dạng. Cách sửa: đăng nhập lại để lấy token mới.
- **403 Forbidden**: Server biết chính xác bạn là ai, nhưng bạn không có quyền thực hiện hành động này. Cách sửa: tài khoản của bạn cần quyền cao hơn.

Mẹo kiểm thử: luôn viết hai test case âm tính riêng biệt — 401 (không có token) và 403 (sai role).
</Vi>

# Simulating HTTP concepts before using real HTTP libraries (Day 40)
# This illustrates the structure without making real network calls

def build_request(method: str, url: str, headers: dict = None, body: dict = None) -> dict:
    return {
        "method": method.upper(),
        "url": url,
        "headers": headers or {"Content-Type": "application/json"},
        "body": body,

    return {
        "status_code": status,

        "body": body,
    }

create_request = build_request(
    "POST",
    "https://api.example.com/users",

**Phần 2 — Phân loại status code và các hàm assertion hỗ trợ**

</Vi>

```python
def is_success(response: dict) -> bool:
    return 200 <= response["status_code"] < 300

def is_client_error(response: dict) -> bool:
    return 400 <= response["status_code"] < 500

def is_server_error(response: dict) -> bool:
    return 500 <= response["status_code"] < 600

def classify(response: dict) -> str:
    code = response["status_code"]
    if 200 <= code < 300:
        return "success"
    elif 400 <= code < 500:
        return "client error"
    elif 500 <= code < 600:
        return "server error"
    return "unknown"

# Basic assertions — the kind you'll write in real tests
assert is_success(success_201),        "Expected 201 to be success"
assert not is_success(auth_error),     "Expected 401 to not be success"
assert is_client_error(auth_error),    "Expected 401 to be client error"
assert is_client_error(forbidden),     "Expected 403 to be client error"
assert is_server_error(server_error),  "Expected 500 to be server error"

# 401 vs 403 distinction
assert auth_error["status_code"] == 401,  "No token → 401"
assert forbidden["status_code"] == 403,   "Wrong role → 403"

# Classify all responses
all_responses = [success_201, auth_error, forbidden, not_found, conflict, server_error]
for resp in all_responses:
    code = resp["status_code"]
    print(f"  {code} → {classify(resp)}")
```

**Part 3 — Simulating PATCH vs PUT behaviour**

</En>
<Vi>

**Phần 3 — Mô phỏng hành vi PATCH so với PUT**

</Vi>

```python
# Illustrates the semantic difference between PUT and PATCH

stored_user = {
    "id": 42,
    "email": "alice@example.com",
    "name": "Alice Smith",
    "role": "admin",
    "is_active": True,
}

def apply_put(current: dict, payload: dict) -> dict:
    """PUT replaces the entire resource — fields not in payload become None."""
    return {"id": current["id"], **payload}

def apply_patch(current: dict, payload: dict) -> dict:
    """PATCH merges — only the provided fields are updated."""
    return {**current, **payload}

# PUT with a partial payload — name and role are wiped out
put_result = apply_put(stored_user, {"email": "alice@new.com"})
print("After PUT: ", put_result)
# {"id": 42, "email": "alice@new.com"}  ← name, role, is_active gone!

# PATCH with a partial payload — only email changes
patch_result = apply_patch(stored_user, {"email": "alice@new.com"})
print("After PATCH:", patch_result)
# {"id": 42, "email": "alice@new.com", "name": "Alice Smith", "role": "admin", "is_active": True}

# Test assertions
assert "name" not in put_result or put_result.get("name") is None, \
    "PUT should not preserve fields not in payload"
assert patch_result["name"] == "Alice Smith", \
    "PATCH must preserve fields not in payload"
assert patch_result["email"] == "alice@new.com", \
    "PATCH must update the provided field"

print("PATCH vs PUT assertions passed!")
```
