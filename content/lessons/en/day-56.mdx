**Why a green CI badge matters more than a code coverage number**

Recruiters and hiring managers spend 30–60 seconds on a GitHub repository before deciding whether to read further. A green CI badge — the little shield that says `passing` — communicates something that a coverage percentage cannot: the project actually runs. Coverage numbers only show how much code tests exercise; they say nothing about whether the tests are meaningful, whether the environment is reproducible, or whether a fresh clone on a different machine produces the same result.

A green badge proves all of those things at once. It means your dependencies are pinned, your environment is reproducible, your tests are not silently skipped, and someone (the CI runner) has independently verified the project since your last commit. That is a trust signal. Code coverage of 85% with no CI is much weaker evidence than 70% coverage with a badge that has been green for every commit for six months.

This is why setting up GitHub Actions on day one of a new project — before writing a single test — is a professional habit worth building. An always-green CI history is a record of your engineering discipline.

---

**How to make a QA portfolio stand out**

Most self-taught QA portfolios test the same handful of apps (Pet Store API, a todo list, or a signup form) with the same happy-path flows. A portfolio that stands out does three things differently:

1. **Tests a real, interesting target.** ReqRes.in (which you used in this course) is a solid training API, but for a portfolio project, pick something that has both an API and a UI — an open-source app you can run locally, or a public API with enough depth (authentication, pagination, error states, rate limiting) to write 20+ meaningful test cases.

2. **Covers negative and edge cases explicitly.** A generic test suite asserts that `POST /users` with valid data returns 201. A standout portfolio also asserts that it returns 422 when required fields are missing, 400 when the email format is invalid, and (for authenticated endpoints) 401 when the token is absent. Negative test coverage tells a reviewer that you understand how systems fail, not just how they work when everything is correct.

3. **Shows test plan thinking.** Attach a `TEST_PLAN.md` that describes your risk assessment: what you tested, why, what you left out and why, and what the riskiest areas are. A hiring manager who reads your test plan learns more about your thinking than they can from reading fifty test files. Test code shows you can automate; a test plan shows you can think like a QA engineer.

**What "senior QA engineer" actually means in practice**

The word "senior" in QA is not about knowing more tools. It is about a shift from executing tests to predicting risk. A junior QA engineer asks "did this feature work as specified?". A senior QA engineer asks "given how this system is built, where is the most likely place for something to break, and how would we know before a user reports it?".

In practice this means:

- **Reading code, not just testing it.** A senior QA reads the implementation of a feature to understand what assumptions the developer made. Those assumptions are where bugs hide.
- **Attending planning meetings, not just reviewing tickets.** The earlier in the SDLC a QA engineer identifies a risk, the cheaper it is to address. A bug caught in a planning discussion costs minutes. The same bug caught in production costs hours of engineer time, user trust, and possibly revenue.
- **Communicating in business terms.** A senior QA does not say "we have 12 failing tests". They say "the payment flow has a known failure case when a user's session expires at checkout — this affects approximately 2% of transactions based on session analytics". That framing gets attention and action.
- **Treating the test framework as a product.** The framework has users (the engineering team). It needs documentation, onboarding, and maintenance. A senior QA designs it so that adding a new test for a new endpoint takes five minutes, not fifty.

**How to prepare for ISTQB Foundation Level (CTFL)**

ISTQB CTFL is the most widely recognised entry-level QA certification globally. Most employers list it as "preferred" or "an advantage" for QA roles. After completing this course, you are already familiar with most of the content — you have been practising it for 56 days.

Key topic areas in the CTFL syllabus (2023 version):

| Chapter | Weight | What you already know |
|---------|--------|-----------------------|
| Fundamentals of testing | ~26% | Testing objectives, test pyramid, bug lifecycle |
| Testing throughout the SDLC | ~17% | V-model, Agile testing, shift-left |
| Static testing | ~12% | Reviews, walkthroughs (lighter in this course) |
| Test analysis and design | ~25% | Equivalence partitioning, boundary value analysis, decision tables |
| Managing the test activities | ~10% | Test planning, test estimation, risk-based testing |
| Test tools | ~10% | Tool classification, selection criteria |

**Recommended study timeline after this course:** 4–6 weeks. Spend the first two weeks reading the official CTFL syllabus (free PDF from istqb.org). Spend weeks three and four working through sample exam questions — the ISTQB website publishes official sample papers. Spend the final two weeks taking timed mock exams and reviewing weak areas. The exam is 40 multiple-choice questions in 60 minutes, with a passing score of 65%.

**Tại sao badge CI xanh quan trọng hơn số code coverage**

Nhà tuyển dụng và người quản lý tuyển dụng chỉ dành 30–60 giây xem một repository GitHub trước khi quyết định có đọc tiếp không. Badge CI xanh — cái huy hiệu nhỏ ghi `passing` — truyền đạt điều mà phần trăm coverage không thể: dự án thực sự chạy được. Số coverage chỉ cho thấy code test thực thi bao nhiêu; chúng không nói gì về việc test có ý nghĩa không, môi trường có thể tái tạo không, hoặc clone mới trên máy khác có cho kết quả tương tự không.

Badge xanh chứng minh tất cả những điều đó cùng một lúc. Nó có nghĩa là dependencies của bạn được ghim phiên bản, môi trường có thể tái tạo, test không bị bỏ qua âm thầm, và ai đó (CI runner) đã kiểm tra độc lập dự án từ commit cuối cùng của bạn. Đó là tín hiệu tin tưởng.

**Cách làm portfolio QA nổi bật**

Hầu hết portfolio QA tự học đều test cùng một vài app (Pet Store API, todo list, form đăng ký) với cùng những flow happy-path. Portfolio nổi bật làm ba điều khác biệt:

1. **Test target thực và thú vị.** Chọn thứ gì đó có cả API lẫn UI với đủ chiều sâu để viết 20+ test case có ý nghĩa.
2. **Bao phủ rõ ràng các trường hợp tiêu cực và edge case.** Test cover tiêu cực cho thấy bạn hiểu hệ thống thất bại như thế nào, không chỉ khi mọi thứ đúng.
3. **Thể hiện tư duy test plan.** Đính kèm `TEST_PLAN.md` mô tả đánh giá rủi ro: bạn test gì, tại sao, bỏ qua gì và lý do, đâu là vùng rủi ro nhất.

**"Kỹ sư QA cấp senior" thực sự có nghĩa gì trong thực tế**

Từ "senior" trong QA không phải về việc biết nhiều tool hơn. Đó là sự chuyển dịch từ thực thi test sang dự đoán rủi ro. Kỹ sư QA junior hỏi "tính năng này có hoạt động đúng spec không?". Kỹ sư QA senior hỏi "với cách hệ thống này được xây dựng, đâu là nơi có khả năng xảy ra lỗi nhất, và chúng ta sẽ biết trước khi người dùng báo cáo không?".

Trong thực tế điều này có nghĩa là:
- Đọc code, không chỉ test nó
- Tham dự các cuộc họp lập kế hoạch, không chỉ review ticket
- Giao tiếp theo ngôn ngữ kinh doanh
- Coi framework test như một sản phẩm
