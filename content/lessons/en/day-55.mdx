## Concept

<En>
**Why the CRUD checklist matters — the missing DELETE problem:**

A common trap is testing Create and Read heavily but skipping Update and Delete. The reasoning is usually "delete is obvious, it either works or it doesn't." But untested behavior is unverified behavior. If your application introduces a soft-delete feature (marking records as deleted instead of removing them), a regression in DELETE that starts returning 200 instead of 204, or a bug where deleting a user does not cascade to their related records — none of that is caught by your suite until a user reports it in production.

The full checklist for each resource:

| Test | Why it matters |
|------|---------------|
| List (GET all) | Confirms pagination contract and field presence across a collection |
| Get by ID (GET one) | Confirms a known-good ID returns data with correct schema |
| Create (POST → 201) | Confirms the server persists the resource and returns the new ID |
| Update (PUT/PATCH → 200) | Confirms the right fields change and irrelevant fields are untouched |
| Delete (DELETE → 204) | Confirms the resource is gone; follow up with GET to verify 404 |
| Not found (GET invalid → 404) | Confirms the error contract — clients depend on this status code |
| Validation failure (POST bad data → 400/422) | Confirms the API rejects bad input rather than silently accepting it |

**Why integration tests beat pure UI for data setup:**

Creating a user through the UI means: navigate, find the form, fill 5 fields, click submit, wait for redirect, confirm the page loaded. That sequence takes 3–5 seconds on a fast machine and more on CI. The same operation via API takes 50–150 ms.

But integration tests are not about speed alone. When the UI registration form is broken, a pure UI test for "login after registration" would fail at the registration step — leaving you uncertain whether the login feature itself works. An integration test that uses the API for setup bypasses the broken form entirely. If login fails, you know login is the bug, not registration.

The pattern:
```
1. [API]  POST /users → create test user, save ID
2. [UI]   Navigate to login, use the test user's credentials
3. [UI]   Assert the dashboard or profile is correct
4. [API]  DELETE /users/{id} → clean up (optional — depends on test isolation strategy)
```

**Why separate CI jobs for API and UI:**

If all tests run in one sequential job, total CI time equals API time + UI time + browser install time. With parallel jobs:
- `api-tests` job: no browser needed, runs in ~2 minutes
- `ui-tests` job: installs Chromium, runs in ~8 minutes
- Total wall-clock time: ~8 minutes (not 10+)

More importantly, a flaky UI test (browser timeout, network hiccup) does not block visibility of API results. Your team can see the green API job and know the API layer is healthy while the UI flake is being investigated. Failure isolation is the real benefit of separate jobs.

**Why pytest marks need to be registered in pytest.ini:**

If you use `@pytest.mark.api` without registering it, every test run prints:

```
PytestUnknownMarkWarning: Unknown pytest.mark.api - is this a typo?
```

This is a warning, not an error, but it clutters CI output and, more importantly, indicates that `pytest -m api` may not reliably select only your API tests — unregistered marks silently fall through. Registering marks in `pytest.ini` makes the selection deterministic and silences the warning:

```ini
[pytest]
markers =
    api: marks tests as API-layer tests (deselect with -m "not api")
    ui:  marks tests as UI/browser tests (deselect with -m "not ui")
    integration: marks tests that combine API setup with UI verification
```

**The complete API test strategy for ReqRes.in:**

ReqRes.in (`https://reqres.in/api`) is a public mock API that simulates a real backend. It is stable, always available, and returns realistic response schemas. Key behaviors:
- GET /users?page=1 returns paginated results with `data`, `total`, `per_page`
- POST /users returns a 201 with `id` and `createdAt` fields (ReqRes generates these)
- `DELETE /users/{id}` returns 204 No Content (no body)
- GET /users/9999 returns 404 (not found)
- POST /login without `password` returns 400 with `"error"` key

These cover every row in the CRUD checklist above.
</En>
<Vi>
**Tại sao CRUD checklist quan trọng — vấn đề DELETE bị bỏ qua:**

Bẫy phổ biến là test Create và Read nhiều nhưng bỏ qua Update và Delete. Lý do thường là "delete rõ ràng rồi, nó hoặc hoạt động hoặc không." Nhưng hành vi chưa được test là hành vi chưa được xác minh. Nếu ứng dụng của bạn giới thiệu tính năng soft-delete (đánh dấu record là đã xóa thay vì xóa thật), regression trong DELETE bắt đầu trả về 200 thay vì 204, hoặc bug nơi xóa user không cascade sang các record liên quan — không có gì trong số đó được bắt bởi suite cho đến khi user báo cáo trong production.

Checklist đầy đủ cho mỗi tài nguyên:

| Test | Tại sao quan trọng |
|------|-------------------|
| List (GET tất cả) | Xác nhận contract phân trang và sự hiện diện field trên collection |
| Get by ID (GET một) | Xác nhận ID đã biết trả về dữ liệu với schema đúng |
| Create (POST → 201) | Xác nhận server lưu tài nguyên và trả về ID mới |
| Update (PUT/PATCH → 200) | Xác nhận các field đúng thay đổi và field không liên quan không bị ảnh hưởng |
| Delete (DELETE → 204) | Xác nhận tài nguyên đã biến mất; theo dõi bằng GET để xác minh 404 |
| Not found (GET không hợp lệ → 404) | Xác nhận contract lỗi — client phụ thuộc vào status code này |
| Lỗi validation (POST dữ liệu xấu → 400/422) | Xác nhận API từ chối input xấu thay vì chấp nhận im lặng |

**Tại sao test tích hợp tốt hơn UI thuần cho thiết lập dữ liệu:**

Tạo user qua UI nghĩa là: điều hướng, tìm form, điền 5 trường, click submit, chờ redirect, xác nhận trang đã load. Chuỗi đó mất 3–5 giây trên máy nhanh và nhiều hơn trên CI. Cùng thao tác qua API mất 50–150 ms.

Pattern:
```
1. [API]  POST /users → tạo user test, lưu ID
2. [UI]   Điều hướng đến login, dùng thông tin xác thực của user test
3. [UI]   Assert dashboard hoặc hồ sơ đúng
4. [API]  DELETE /users/{id} → dọn dẹp (tuỳ chọn)
```

**Tại sao các job CI riêng biệt cho API và UI:**

Với job song song:
- Job `api-tests`: không cần browser, chạy trong ~2 phút
- Job `ui-tests`: cài Chromium, chạy trong ~8 phút
- Tổng thời gian wall-clock: ~8 phút (không phải 10+)

Quan trọng hơn, UI test flaky (browser timeout, sự cố mạng) không chặn khả năng xem kết quả API. Team của bạn có thể thấy job API xanh và biết lớp API khỏe mạnh trong khi UI flake đang được điều tra. Cô lập thất bại là lợi ích thực sự của các job riêng biệt.

**Tại sao pytest mark cần được đăng ký trong pytest.ini:**

Nếu bạn dùng `@pytest.mark.api` mà không đăng ký nó, mỗi lần chạy test in ra `PytestUnknownMarkWarning`. Đăng ký mark trong `pytest.ini` làm cho việc chọn lọc có tính quyết định và tắt cảnh báo.
</Vi>

**Part 1 — test_auth.py: authentication endpoint coverage**

Authentication is the gateway to everything else in the API. A broken login means no token, which means all authenticated endpoint tests would fail with 401 — making it impossible to distinguish auth failures from feature failures. Always test auth first in your CRUD checklist.

</En>
<Vi>

**Phần 1 — test_auth.py: bao phủ endpoint xác thực**

Xác thực là cổng vào mọi thứ khác trong API. Login bị hỏng nghĩa là không có token, nghĩa là tất cả test endpoint có xác thực sẽ thất bại với 401 — không thể phân biệt auth failure với feature failure. Luôn test auth trước trong CRUD checklist.

</Vi>

```python
# tests/api/test_auth.py
import allure
import pytest
from api.client import ApiClient

# ReqRes.in registered test accounts — these are baked into the mock API.
VALID_EMAIL = "eve.holt@reqres.in"
VALID_PASSWORD_LOGIN = "cityslicka"
VALID_PASSWORD_REGISTER = "pistol"


@allure.epic("ReqRes API")
@allure.feature("Auth")
class TestAuth:
    """Authentication endpoint tests.

    Covers the happy path (returns token), missing required field (400),
    and registration success. These are CRITICAL — if auth breaks, all
    tests that depend on authenticated calls will fail with misleading errors.
    """

    @allure.story("Login")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.api
    def test_login_returns_token(self, api: ApiClient) -> None:
        """Valid login credentials must return HTTP 200 and a non-empty token."""
        payload = {"email": VALID_EMAIL, "password": VALID_PASSWORD_LOGIN}

        with allure.step("POST /login with valid credentials"):
            response = api.post("/login", json=payload)

        with allure.step("Assert 200 status and token present in body"):
            assert response.status_code == 200, (
                f"Expected 200, got {response.status_code}. Body: {response.text}"
            )
            body = response.json()
            assert "token" in body, f"Response body missing 'token' key: {body}"
            assert len(body["token"]) > 0, "Token must not be an empty string"

    @allure.story("Login")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_login_missing_password_returns_400(self, api: ApiClient) -> None:
        """Submitting email without password must return 400 with an error message.

        This validates the server-side validation contract. Clients depend
        on the error key to display meaningful messages.
        """
        response = api.post("/login", json={"email": VALID_EMAIL})

        assert response.status_code == 400, (
            f"Expected 400 for missing password, got {response.status_code}"
        )
        body = response.json()
        assert "error" in body, f"Expected 'error' key in body: {body}"
        assert len(body["error"]) > 0, "Error message must not be empty"

    @allure.story("Login")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_login_missing_email_returns_400(self, api: ApiClient) -> None:
        """Submitting only password (no email) must also return 400."""
        response = api.post("/login", json={"password": VALID_PASSWORD_LOGIN})

        assert response.status_code == 400
        assert "error" in response.json()

    @allure.story("Register")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.api
    def test_register_success(self, api: ApiClient) -> None:
        """Valid registration must return 200 with both id and token."""
        payload = {"email": VALID_EMAIL, "password": VALID_PASSWORD_REGISTER}

        with allure.step("POST /register with valid payload"):
            response = api.post("/register", json=payload)

        with allure.step("Assert 200 and response contains id + token"):
            assert response.status_code == 200
            body = response.json()
            assert "id" in body, f"Missing 'id' in register response: {body}"
            assert "token" in body, f"Missing 'token' in register response: {body}"
            assert isinstance(body["id"], int), "id must be an integer"

    @allure.story("Register")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_register_missing_password_returns_400(self, api: ApiClient) -> None:
        """Registration without password must return 400 with error."""
        response = api.post("/register", json={"email": VALID_EMAIL})

        assert response.status_code == 400
        assert "error" in response.json()
```

**Phần 2 — test_users_crud.py: CRUD đầy đủ với schema validation và parametrize**

Đây là cốt lõi của lớp API test. Mọi hàng trong CRUD checklist đều được bao phủ. `@pytest.mark.parametrize` tạo các test case độc lập, được báo cáo riêng lẻ từ danh sách input — nếu user ID 2 thất bại nhưng 1 và 3 pass, báo cáo thất bại chính xác.

```python
# tests/api/test_users_crud.py
import allure
import pytest
from jsonschema import validate, ValidationError
from api.client import ApiClient

# JSON Schema for a single user object inside the 'data' key.
# This is the contract the API promises to its clients.
SINGLE_USER_SCHEMA = {
    "type": "object",
    "required": ["id", "email", "first_name", "last_name", "avatar"],
    "properties": {
        "id":         {"type": "integer"},
        "email":      {"type": "string", "format": "email"},
        "first_name": {"type": "string", "minLength": 1},
        "last_name":  {"type": "string", "minLength": 1},
        "avatar":     {"type": "string", "format": "uri"},
    },
    "additionalProperties": False,
}

LIST_RESPONSE_SCHEMA = {
    "type": "object",
    "required": ["data", "total", "per_page", "page"],
    "properties": {
        "data":     {"type": "array"},
        "total":    {"type": "integer"},
        "per_page": {"type": "integer"},
        "page":     {"type": "integer"},
    },
}

CREATE_RESPONSE_SCHEMA = {
    "type": "object",
    "required": ["name", "job", "id", "createdAt"],
    "properties": {
        "name":      {"type": "string"},
        "job":       {"type": "string"},
        "id":        {"type": "string"},   # ReqRes returns id as string on POST
        "createdAt": {"type": "string"},
    },
}


def assert_schema(data: dict, schema: dict, label: str = "") -> None:
    """Validate data against schema and raise a descriptive AssertionError on failure."""
    try:
        validate(instance=data, schema=schema)
    except ValidationError as e:
        raise AssertionError(
            f"Schema validation failed{' for ' + label if label else ''}: {e.message}"
        ) from e


@allure.epic("ReqRes API")
@allure.feature("Users CRUD")
class TestUsersCRUD:
    """Full CRUD coverage for the /users resource.

    Run with: pytest tests/api/ -v -m api
    """

    # ------------------------------------------------------------------
    # READ — List
    # ------------------------------------------------------------------

    @allure.story("Read")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.api
    def test_list_users_page_1(self, api: ApiClient) -> None:
        """GET /users?page=1 must return paginated data with correct structure."""
        with allure.step("GET /users?page=1"):
            response = api.get("/users", params={"page": 1})

        with allure.step("Assert 200 and validate list schema"):
            assert response.status_code == 200
            body = response.json()
            assert_schema(body, LIST_RESPONSE_SCHEMA, label="list users response")
            assert isinstance(body["data"], list), "data must be a list"
            assert len(body["data"]) > 0, "Page 1 must contain at least one user"
            assert body["total"] > 0, "total must be positive"

    @allure.story("Read")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    @pytest.mark.parametrize("page,expected_count", [(1, 6), (2, 6)])
    def test_pagination(self, api: ApiClient, page: int, expected_count: int) -> None:
        """Each page of /users must return exactly 6 users (ReqRes contract)."""
        response = api.get("/users", params={"page": page})
        assert response.status_code == 200
        data = response.json()["data"]
        assert len(data) == expected_count, (
            f"Page {page}: expected {expected_count} users, got {len(data)}"
        )

    # ------------------------------------------------------------------
    # READ — Get by ID
    # ------------------------------------------------------------------

    @allure.story("Read")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.api
    @pytest.mark.parametrize("user_id", [1, 2, 3])
    def test_get_user_by_id(self, api: ApiClient, user_id: int) -> None:
        """GET /users/{id} for a valid ID must return 200 and a conforming schema."""
        with allure.step(f"GET /users/{user_id}"):
            response = api.get(f"/users/{user_id}")

        with allure.step("Assert 200 and validate user schema"):
            assert response.status_code == 200
            body = response.json()
            assert "data" in body, f"Response missing 'data' key: {body}"
            assert_schema(body["data"], SINGLE_USER_SCHEMA, label=f"user/{user_id}")
            # Extra business assertion: the returned id must match the requested id
            assert body["data"]["id"] == user_id, (
                f"Returned id {body['data']['id']} does not match requested id {user_id}"
            )

    @allure.story("Read")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_get_user_not_found(self, api: ApiClient) -> None:
        """GET /users/{invalid_id} must return 404.

        Clients depend on 404 to distinguish 'resource missing' from other errors.
        A server that returns 200 with empty body breaks client error handling.
        """
        response = api.get("/users/9999")
        assert response.status_code == 404, (
            f"Expected 404 for non-existent user, got {response.status_code}"
        )

    # ------------------------------------------------------------------
    # CREATE
    # ------------------------------------------------------------------

    @allure.story("Create")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.api
    def test_create_user(self, api: ApiClient) -> None:
        """POST /users must return 201 and the created resource with server-generated fields."""
        payload = {"name": "Capstone QA Engineer", "job": "automation"}

        with allure.step("POST /users with name and job"):
            response = api.post("/users", json=payload)

        with allure.step("Assert 201 and validate create response schema"):
            assert response.status_code == 201, (
                f"Expected 201 Created, got {response.status_code}. Body: {response.text}"
            )
            body = response.json()
            assert_schema(body, CREATE_RESPONSE_SCHEMA, label="create user response")
            # Server must echo back exactly what we sent
            assert body["name"] == payload["name"]
            assert body["job"] == payload["job"]
            # Server must generate an id (non-empty string in ReqRes)
            assert len(body["id"]) > 0, "Server must assign a non-empty id"

    @allure.story("Create")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    @pytest.mark.parametrize("payload,description", [
        ({"name": "Test User"}, "job field missing"),
        ({}, "empty body"),
    ])
    def test_create_user_partial_payload(
        self, api: ApiClient, payload: dict, description: str
    ) -> None:
        """ReqRes accepts partial payloads for POST /users.

        This test documents the actual behavior: ReqRes is lenient and
        returns 201 even for partial payloads. A stricter real API would
        return 400/422 here — adjust assertions to match your target API's contract.
        """
        response = api.post("/users", json=payload)
        # Document the actual behavior — ReqRes does not validate required fields
        assert response.status_code == 201, (
            f"ReqRes returned {response.status_code} for {description}"
        )

    # ------------------------------------------------------------------
    # UPDATE
    # ------------------------------------------------------------------

    @allure.story("Update")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_update_user_put(self, api: ApiClient) -> None:
        """PUT /users/{id} must return 200 and reflect the updated fields."""
        payload = {"name": "Updated Full Name", "job": "senior automation engineer"}

        with allure.step("PUT /users/2 with updated name and job"):
            response = api.put("/users/2", json=payload)

        with allure.step("Assert 200 and updated fields are reflected"):
            assert response.status_code == 200
            body = response.json()
            assert body["name"] == payload["name"], (
                f"name not updated. Got: {body['name']}"
            )
            assert body["job"] == payload["job"], (
                f"job not updated. Got: {body['job']}"
            )
            # ReqRes adds updatedAt to the response — verify it is present
            assert "updatedAt" in body, "Response must include updatedAt timestamp"

    @allure.story("Update")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_update_user_patch(self, api: ApiClient) -> None:
        """PATCH /users/{id} must return 200 for a partial update."""
        payload = {"job": "QA lead"}

        response = api.patch("/users/2", json=payload)

        assert response.status_code == 200
        assert response.json()["job"] == payload["job"]
        assert "updatedAt" in response.json()

    # ------------------------------------------------------------------
    # DELETE
    # ------------------------------------------------------------------

    @allure.story("Delete")
    @allure.severity(allure.severity_level.NORMAL)
    @pytest.mark.api
    def test_delete_user(self, api: ApiClient) -> None:
        """DELETE /users/{id} must return 204 No Content.

        204 means 'done, nothing to return' — the correct status for a
        successful delete. A 200 with an empty body is technically acceptable
        in some APIs but 204 is the REST-idiomatic choice.
        Note: always test DELETE separately from your GET-by-ID test to
        avoid test ordering issues.
        """
        with allure.step("DELETE /users/2"):
            response = api.delete("/users/2")

        with allure.step("Assert 204 No Content"):
            assert response.status_code == 204, (
                f"Expected 204 for delete, got {response.status_code}"
            )
            # 204 responses must have no body
            assert response.text == "" or response.content == b"", (
                f"204 response must have empty body, got: {response.text}"
            )
```

The two jobs run in parallel. The `api-tests` job completes in ~2 minutes; the `ui-tests` job installs Chromium and completes in ~8–10 minutes. Total CI time is the duration of the slower job, not the sum — a significant improvement over a single sequential job.

**Phần 3 — GitHub Actions CI: job API và UI song song**

Hai job chạy song song. Job `api-tests` hoàn thành trong ~2 phút; job `ui-tests` cài Chromium và hoàn thành trong ~8–10 phút. Tổng thời gian CI là thời gian của job chậm hơn, không phải tổng — cải thiện đáng kể so với một job tuần tự duy nhất.

</Vi>

```yaml
# .github/workflows/tests.yml
name: Capstone Test Suite

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  # ----------------------------------------------------------------
  # API tests — no browser needed, fast job (~2 min)
  # ----------------------------------------------------------------
  api-tests:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python 3.11
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"

      - name: Install Python dependencies
        run: pip install -r requirements.txt

      - name: Run API tests
        run: |
          pytest tests/api/ \
            -v \
            --tb=short \
            -m api \
            --alluredir=allure-results \
            --junit-xml=api-results.xml

      - name: Upload Allure results
```

Without registered markers, `pytest -m api` still works but prints `PytestUnknownMarkWarning` on every run. </En>
