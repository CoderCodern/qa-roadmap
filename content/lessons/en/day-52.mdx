## Intro

<En>
Automation is not everything. Before writing a single test, a professional QA engineer writes a test plan — a document that defines scope, strategy, resources, and risk. A test plan is not bureaucracy for its own sake. It is the engineering artifact that makes three things possible: it aligns stakeholders on what success looks like before work starts, it prevents scope creep during development, and it makes the question "are we done?" answerable with objective criteria rather than gut feel. In interviews and on teams, the ability to write a clear test plan is what demonstrates senior-level thinking. Today you write a test plan for your capstone project.
</En>
<Vi>
Tự động hoá không phải là tất cả. Trước khi viết một test nào, kỹ sư QA chuyên nghiệp viết kế hoạch test — tài liệu định nghĩa phạm vi, chiến lược, tài nguyên và rủi ro. Kế hoạch test không phải là thủ tục hành chính vô nghĩa. Đó là tài liệu kỹ thuật giúp ba điều có thể thực hiện được: căn chỉnh các bên liên quan về thành công trông như thế nào trước khi công việc bắt đầu, ngăn chặn phình to phạm vi trong quá trình phát triển và làm cho câu hỏi "chúng ta hoàn thành chưa?" có thể trả lời được bằng tiêu chí khách quan thay vì cảm tính. Trong phỏng vấn và trong nhóm, khả năng viết kế hoạch test rõ ràng là điều thể hiện tư duy ở cấp độ senior. Hôm nay bạn viết kế hoạch test cho capstone project của mình.
</Vi>

## Concept

<En>
**Why test plans exist — the engineering reasoning**

Without a test plan, testing is undefined work. You don't know when to start, when to stop, or what counts as success. Teams without test plans tend to hit these failure modes:

- **Scope creep**: a developer says "can you also test the payment module?" halfway through — with no plan, there is no documented reason to say no.
- **Premature sign-off**: testing ends because time ran out, not because quality was demonstrated — the plan's exit criteria prevent this.
- **Rework**: QA discovers the test environment was never set up, or credentials were never provisioned — entry criteria catch this before work starts.
- **Hidden risk**: no one explicitly asked "what happens if the third-party SMS service is unavailable during testing?" — the risk section forces this conversation.

A test plan is a contract. It tells the team what you will test, how you will test it, and what "done" means.

---

**Section 1 — Objective**

The objective answers: *what are we testing and what does success look like?*

A weak objective: "Test the login feature."

A strong objective: "Verify that the login endpoint correctly authenticates valid credentials, rejects invalid credentials with appropriate HTTP status codes, and enforces rate limiting after 5 failed attempts — providing automated regression coverage that runs on every CI push."

The difference is specificity. A vague objective cannot fail or succeed — it floats. A specific objective lets you look at your test results and say definitively "we achieved this" or "we did not."

---

**Section 2 — Scope: the engineering judgment section**

Scope is where you make explicit decisions about what to include and exclude. The out-of-scope list is more important than it looks — it is where you document trade-offs and risk acceptance decisions.

- **In scope**: endpoints, user flows, data scenarios, environments, and failure modes your tests will cover.
- **Out of scope**: what you are explicitly *not* testing — and critically, *why not*.

Examples of defensible out-of-scope decisions:
- "Load testing — out of scope because we have no production traffic baseline and no staging environment capable of receiving realistic load."
- "Database-level testing — out of scope because we have no direct DB access; covered by integration tests in the backend team's scope."

Unstated out-of-scope items become implied commitments. If you don't say "load testing is out of scope," stakeholders may assume you covered it.

---

**Section 3 — Test approach / strategy**

This section documents *how* you will test. It covers:

- **Test levels**: unit (isolated logic), integration (service-to-service), E2E (full user journey)
- **Test types**: functional (does it work?), negative (does it fail correctly?), regression (does the old stuff still work?), schema (does the response match the contract?)
- **Tools**: pytest + requests for API, Playwright for UI, jsonschema for schema validation, Allure for reporting
- **Data strategy**: how test data is created, isolated, and cleaned up. This matters because shared mutable test data causes intermittent failures.

For ReqRes.in: test data is simulated (the API doesn't persist writes), so cleanup is a non-issue. For a real app with a database, you'd document how each test seeds and teardowns its own data.

---

**Section 4 — Test environment**

This section prevents the most common reason testing is delayed: "the environment wasn't ready." It documents:

- Which environment tests run against (staging, production, local mock)
- What credentials and access are required (API keys, user accounts, VPN access)
- What external dependencies exist (third-party APIs, email services, SMS gateways)
- What tool versions are required (Python 3.11+, Node 20+)

Entry criteria (next section) depend directly on the environment section — you can't check "API is reachable" without knowing which API URL to check.

---

**Section 5 — Entry and exit criteria: making "done" objective**

This is the most consequential section, and the one most often skipped on junior teams.

**Entry criteria** define the preconditions that must be true before testing begins. Without them, testing starts prematurely and wastes time on environment problems:
- All dependencies installed and verified
- Target environment is up and reachable
- Test data seeded (if required)
- Credentials provisioned

**Exit criteria** define what "done" means for testing. Without them, testing either ends arbitrarily ("we ran out of time") or never ends ("there might be more bugs"). Clear, measurable exit criteria make sign-off an objective decision:

Weak exit criteria (avoid): "All tests are passing and quality looks good."

Strong exit criteria (use these patterns):
- All planned test cases executed
- 0 open Critical or High severity defects
- CI pipeline green for 3 consecutive runs
- Allure report generated and reviewed by the team
- Test coverage ≥ 80% of in-scope endpoints

The distinction matters: "quality looks good" is a feeling. "0 Critical bugs open and CI green" is a fact.

---

**Section 6 — Risk and mitigation: quantifying the unknown**

Risk analysis forces you to think adversarially about your own plan. The discipline is to assess each risk on two axes: **likelihood** (how probable?) and **impact** (how bad if it happens?). Priority = likelihood × impact.

| Risk | Likelihood | Impact | Score | Mitigation |
|------|-----------|--------|-------|------------|
| Target API has downtime during CI run | Medium | High | 6 | Mark as external-dependency flake; run with retry |
| API response schema changes without notice | Low | High | 4 | Pin schema files in version control; alert on schema drift |
| Test data collisions when tests run in parallel | High | Medium | 6 | Use unique IDs (uuid4) per run; avoid shared mutable state |
| Credentials expire mid-sprint | Low | Medium | 2 | Store in CI secrets; document rotation schedule |

Listing risks is not pessimism — it is proof that you thought through failure modes before they happened. In a team setting, this section often triggers important conversations ("oh, we don't have a staging environment yet").

---

**Section 7 — Deliverables**

An explicit list of what the testing effort will produce:
- Automated test suite (the code in `/tests/`)
- Allure HTML report
- GitHub Actions CI configuration
- This test plan document itself

Deliverables tell stakeholders what they will actually receive at the end of testing — not just "tests were run."

---

**Section 8 — Roles and responsibilities**

For a solo capstone, this is simple. On a real team it prevents the most common accountability gap — "I thought someone else was doing that":

| Role | Responsibility |
|------|---------------|
| QA Engineer | Test design, automation, Allure report |
| Developer | Code review of test code, bug fixes |
| DevOps / QA | CI pipeline configuration and maintenance |
| QA Lead | Test plan sign-off, exit criteria approval |
</En>
<Vi>
**Tại sao kế hoạch test tồn tại — lý luận kỹ thuật**

Không có kế hoạch test, việc kiểm thử là công việc không xác định. Bạn không biết khi nào bắt đầu, khi nào dừng, hay điều gì được tính là thành công. Các nhóm không có kế hoạch test thường gặp những thất bại này:

- **Phình to phạm vi**: developer nói "bạn cũng có thể test module thanh toán không?" giữa chừng — không có kế hoạch, không có lý do được ghi lại để từ chối.
- **Ký nghiệm thu sớm**: kiểm thử kết thúc vì hết thời gian, không phải vì chất lượng được chứng minh — tiêu chí thoát của kế hoạch ngăn điều này.
- **Làm lại**: QA phát hiện môi trường test chưa bao giờ được thiết lập, hoặc credential chưa bao giờ được cấp — tiêu chí vào bắt được điều này trước khi công việc bắt đầu.
- **Rủi ro ẩn**: không ai hỏi rõ ràng "điều gì xảy ra nếu dịch vụ SMS bên thứ ba không khả dụng trong quá trình kiểm thử?" — phần rủi ro buộc cuộc trò chuyện này xảy ra.

Kế hoạch test là hợp đồng. Nó cho nhóm biết bạn sẽ test gì, cách test như thế nào và "xong" có nghĩa là gì.

---

**Mục 1 — Mục tiêu**

Mục tiêu trả lời: *chúng ta đang kiểm thử gì và thành công trông như thế nào?*

Mục tiêu yếu: "Kiểm thử tính năng đăng nhập."

Mục tiêu mạnh: "Xác minh endpoint đăng nhập xác thực chính xác credential hợp lệ, từ chối credential không hợp lệ với HTTP status code phù hợp và thực thi giới hạn tốc độ sau 5 lần thất bại — cung cấp bao phủ kiểm thử hồi quy tự động chạy trên mỗi CI push."

Sự khác biệt là tính cụ thể. Mục tiêu mơ hồ không thể thất bại hay thành công — nó lơ lửng. Mục tiêu cụ thể cho phép bạn nhìn vào kết quả test và nói dứt khoát "chúng ta đã đạt được điều này" hay "chúng ta chưa đạt."

---

**Mục 2 — Phạm vi: mục đánh giá kỹ thuật**

Phạm vi là nơi bạn đưa ra quyết định rõ ràng về những gì cần bao gồm và loại trừ. Danh sách ngoài phạm vi quan trọng hơn vẻ ngoài — đây là nơi bạn ghi lại các đánh đổi và quyết định chấp nhận rủi ro.

- **Trong phạm vi**: endpoint, luồng người dùng, kịch bản dữ liệu, môi trường và trường hợp lỗi mà test của bạn sẽ bao phủ.
- **Ngoài phạm vi**: những gì bạn *không* kiểm thử một cách rõ ràng — và quan trọng hơn, *tại sao không*.

Ví dụ về quyết định ngoài phạm vi có thể biện hộ:
- "Kiểm thử tải — ngoài phạm vi vì chúng ta không có baseline lưu lượng production và không có môi trường staging có thể nhận tải thực tế."
- "Kiểm thử cấp độ database — ngoài phạm vi vì chúng ta không có quyền truy cập DB trực tiếp; được bao phủ bởi integration test trong phạm vi của nhóm backend."

Các mục ngoài phạm vi không được nêu ra trở thành cam kết ngầm. Nếu bạn không nói "kiểm thử tải ngoài phạm vi," các bên liên quan có thể cho rằng bạn đã bao phủ nó.

---

**Mục 3 — Phương pháp / chiến lược test**

Mục này ghi lại *cách* bạn sẽ test. Bao gồm:

- **Cấp độ test**: unit (logic độc lập), integration (service-to-service), E2E (hành trình người dùng đầy đủ)
- **Loại test**: chức năng (có hoạt động không?), tiêu cực (có thất bại đúng cách không?), hồi quy (những thứ cũ có vẫn hoạt động không?), schema (response có khớp với contract không?)
- **Công cụ**: pytest + requests cho API, Playwright cho UI, jsonschema cho xác thực schema, Allure cho báo cáo
- **Chiến lược dữ liệu**: cách dữ liệu test được tạo, cô lập và dọn dẹp. Điều này quan trọng vì dữ liệu test có thể thay đổi được chia sẻ gây ra lỗi ngẫu nhiên.

---

**Mục 5 — Tiêu chí vào và ra: làm cho "xong" trở nên khách quan**

**Tiêu chí vào** xác định các điều kiện tiên quyết phải đúng trước khi kiểm thử bắt đầu. Không có chúng, kiểm thử bắt đầu quá sớm và lãng phí thời gian vào vấn đề môi trường.

**Tiêu chí ra** xác định "xong" có nghĩa là gì đối với kiểm thử. Không có chúng, kiểm thử kết thúc tùy tiện ("hết thời gian") hoặc không bao giờ kết thúc ("có thể còn bug").

Tiêu chí ra yếu (tránh): "Tất cả test đang vượt qua và chất lượng trông ổn."

Tiêu chí ra mạnh (dùng các mẫu này):
- Tất cả test case theo kế hoạch đã được thực thi
- 0 lỗi Critical hoặc High đang mở
- CI pipeline xanh 3 lần liên tiếp
- Báo cáo Allure được tạo và xem xét bởi nhóm

---

**Mục 6 — Rủi ro và giảm thiểu: định lượng điều chưa biết**

Phân tích rủi ro buộc bạn phải suy nghĩ đối nghịch về kế hoạch của chính mình. Kỷ luật là đánh giá mỗi rủi ro trên hai trục: **khả năng** (xác suất bao nhiêu?) và **tác động** (tệ đến mức nào nếu xảy ra?). Mức ưu tiên = khả năng × tác động.

| Rủi ro | Khả năng | Tác động | Điểm | Giảm thiểu |
|------|-----------|--------|-------|------------|
| API mục tiêu có downtime trong CI | Trung bình | Cao | 6 | Đánh dấu là flake phụ thuộc bên ngoài; chạy với retry |
| Schema response API thay đổi không báo trước | Thấp | Cao | 4 | Ghim file schema trong version control; cảnh báo khi schema drift |
| Xung đột dữ liệu test khi chạy song song | Cao | Trung bình | 6 | Dùng ID duy nhất (uuid4) mỗi lần chạy |
| Credential hết hạn giữa sprint | Thấp | Trung bình | 2 | Lưu trong CI secrets; ghi lại lịch xoay vòng |
</Vi>

```markdown
# Test Plan: ReqRes.in API Suite

**Version:** 1.0
**Date:** 2024-01-15
**Author:** QA Engineer

---

## 1. Objective

Verify that the ReqRes.in REST API correctly handles user management operations
(list, retrieve, create, update, delete) and authentication flows. Provide
automated regression coverage that runs on every CI push and blocks merges
when tests fail.

Success looks like: all planned test cases passing, 0 open Critical/High bugs,
and a green CI pipeline.

---

## 2. Scope

### In scope
- GET /users (list with pagination)
- GET /users/{id} (retrieve single user — valid and invalid ID)
- POST /users (create user)
- PUT /users/{id} (full update)
- PATCH /users/{id} (partial update)
- DELETE /users/{id}
- POST /login (valid credentials, invalid credentials, missing fields)
- POST /register (valid, missing password, missing email)
- Schema validation on all successful GET responses
- Response time assertion (< 3 seconds per request)

### Out of scope
- WebSocket or real-time features — ReqRes.in has none
- Database-level testing — no direct DB access; ReqRes.in is a public mock
- Load / stress testing — no production baseline; out of scope for capstone
- UI testing — ReqRes.in has no testable UI
- Rate limit testing — public API has no meaningful enforced rate limits

---

## 3. Test Approach

| Layer | Tools | Goal |
|-------|-------|------|
| API integration | pytest + requests | 100% of in-scope endpoints |
| Schema validation | jsonschema | All successful GET responses |
| Negative cases | pytest + parametrize | ≥ 3 negative cases per endpoint |
| Reporting | Allure | Every test run |
| CI | GitHub Actions | Every push to main |

**Data strategy:** ReqRes.in simulates persistence — POST/PUT/PATCH/DELETE
appear to succeed but data is not actually stored. Tests are stateless and
require no cleanup. Each test run can repeat indefinitely without pollution.

---

## 4. Test Environment

| Item | Value |
|------|-------|
| Target | https://reqres.in/api |
| Python | 3.11+ |
| Key dependencies | pytest, requests, jsonschema, allure-pytest |
| Credentials | POST /login: `eve.holt@reqres.in` / `cityslicka` |
| External dependencies | ReqRes.in public API (internet required) |
| CI environment | GitHub Actions ubuntu-latest |

---

## 5. Entry / Exit Criteria

### Entry criteria (must be true before testing starts)
- [ ] Python 3.11+ installed and virtual environment activated
- [ ] All dependencies installed: `pip install -r requirements.txt`
- [ ] ReqRes.in API is reachable: `curl https://reqres.in/api/users/1` returns 200
- [ ] `pytest tests/ -v` runs without import errors (even if tests fail)

### Exit criteria (must be true before testing is complete)
- [ ] All planned test cases executed (no skips without documented reason)
- [ ] 0 open Critical or High severity defects
- [ ] CI pipeline green for the last 3 consecutive runs on main
- [ ] Allure report generated and reviewed
- [ ] Test plan reviewed by at least one other person

---

## 6. Risks

| Risk | Likelihood | Impact | Score | Mitigation |
|------|-----------|--------|-------|------------|
| ReqRes.in downtime during CI run | Medium | High | 6 | Retry once on failure; mark as external flake |
| API response schema changes | Low | High | 4 | Schema files in version control; CI alerts on drift |
| Python version mismatch in CI | Low | Medium | 2 | Pin Python version in workflow with `python-version: "3.11"` |
| Test parallelism causing ordering issues | Low | Medium | 2 | Keep tests independent; no shared mutable state |

---

## 7. Deliverables

| Deliverable | Location |
|-------------|----------|
| Automated test suite | `/tests/` |
| Schema files | `/schemas/` |
| Allure raw results | `/allure-results/` |
| CI configuration | `.github/workflows/api-tests.yml` |
| This test plan | `TEST_PLAN.md` |

---

## 8. Roles

| Role | Responsibility |
|------|---------------|
| QA Engineer (you) | Test design, automation, Allure report, CI config |
| Reviewer | Test plan review, code review of test suite |
```

## Risk Scoring Reference

Use this scale when filling in the risk section of your test plan.

### Likelihood scale
| Score | Label | Meaning |
|-------|-------|---------|
| 1 | Low | Unlikely to happen in normal conditions |
| 2 | Medium | Could happen — has happened on similar projects |
| 3 | High | Expected to happen at some point during the project |

### Impact scale
| Score | Label | Meaning |
|-------|-------|---------|
| 1 | Low | Minor inconvenience — easily worked around |
| 2 | Medium | Blocks one person or delays one sprint |
| 3 | High | Blocks the entire team or delays release |

### Risk priority matrix (Likelihood × Impact)
|            | Low Impact (1) | Medium Impact (2) | High Impact (3) |
|------------|---------------|-------------------|-----------------|
| **Low (1)**    | 1 — Monitor   | 2 — Monitor       | 3 — Plan        |
| **Medium (2)** | 2 — Monitor   | 4 — Plan          | 6 — Mitigate    |
| **High (3)**   | 3 — Plan      | 6 — Mitigate      | 9 — Avoid       |

Action guide:
- Score 1–2: Monitor — low priority, document and check periodically
- Score 3–4: Plan — have a response ready; no immediate action needed
- Score 6: Mitigate — act now; put mitigation in place before testing starts
- Score 9: Avoid — redesign to eliminate the risk entirely

### Example risks for a ReqRes.in capstone

| Risk | L | I | Score | Action |
|------|---|---|-------|--------|
| Public API downtime (ReqRes.in is not SLA-guaranteed) | 2 | 3 | 6 | Mitigate: add retry; mark CI failures as expected flake |
| Test data collision (parallel test runs) | 1 | 2 | 2 | Monitor: ReqRes.in doesn't actually persist writes, so no real risk |
| Credentials hardcoded accidentally in code | 1 | 3 | 3 | Plan: use environment variables; add pre-commit secret scan |
| CI runner runs wrong Python version | 1 | 2 | 2 | Monitor: pin `python-version` in workflow YAML |

**Part 3 — Entry and exit criteria: good vs bad examples**

</En>
<Vi>

**Phần 3 — Tiêu chí vào và ra: ví dụ tốt và xấu**

</Vi>

```markdown
## Entry Criteria Examples

### Bad entry criteria (too vague)
- "The application is ready for testing"
- "Developers say the feature is complete"
- "The environment is set up"

Why these fail: they can't be objectively checked. "Ready for testing" means
something different to a developer ("it compiles") and a QA engineer
("all acceptance criteria met, no known blocking bugs, environment verified").

### Good entry criteria (verifiable and specific)
- [ ] All dependencies installed: `pip install -r requirements.txt` exits 0
- [ ] API reachable: `curl https://reqres.in/api/users/1` returns HTTP 200
- [ ] Test suite imports without error: `python -m pytest --collect-only` shows tests
- [ ] Authentication works: POST /login with test credentials returns a token
- [ ] CI pipeline exists and is wired to the main branch

Each item above can be checked by running a command — there is no ambiguity.

---

## Exit Criteria Examples

### Bad exit criteria (too vague)
- "All tests pass"
- "Quality is acceptable"
- "Testing is complete"

Why these fail: "all tests pass" is trivially met by deleting failing tests.
"Quality is acceptable" is not measurable. "Testing is complete" is circular.

### Good exit criteria (measurable and time-bound)
- [ ] All test cases in the test plan executed (no untested items without documented waiver)
- [ ] 0 open P1 (Critical) defects
- [ ] 0 open P2 (High) defects unmitigated
- [ ] CI pipeline: 3 consecutive green runs on the main branch
- [ ] Allure report generated, reviewed, and linked in the PR description
- [ ] Test coverage: ≥ 80% of in-scope endpoints have at least one positive
      and one negative test case

Notice the difference: each criterion above produces a binary yes/no answer
from observable evidence. There is no room for "well, sort of done."
```
