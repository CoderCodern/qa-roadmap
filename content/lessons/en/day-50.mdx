## Intro

<En>
Phase 5 is the capstone — you design and build a complete, professional test framework that integrates everything from the previous four phases. Today you design the framework structure: the folder layout, the layers of abstraction, and the conventions that will make the codebase maintainable as it grows. Good framework design is what separates a collection of test files from a professional test suite. The difference is not how many tests you have — it is how well those tests can survive change.
</En>
<Vi>
Phase 5 là capstone — bạn thiết kế và xây dựng một framework test hoàn chỉnh, chuyên nghiệp tích hợp mọi thứ từ bốn phase trước. Hôm nay bạn thiết kế cấu trúc framework: bố cục thư mục, các lớp trừu tượng và các quy ước làm cho codebase có thể bảo trì khi nó phát triển. Thiết kế framework tốt là điều phân biệt một tập hợp file test với một bộ test chuyên nghiệp. Sự khác biệt không phải là bạn có bao nhiêu test — mà là những test đó có thể tồn tại qua thay đổi tốt như thế nào.

```

**Why layering matters — the dependency graph:**

The four layers form a strict one-way dependency chain:

```
utils  ←  api / pages  ←  tests
                ↑
           conftest.py
```

- `utils` has no imports from any project module — it is pure Python.
- `api` and `pages` import from `utils` but never from `tests`.
- `tests` import from `api`, `pages`, and `utils`. Never from each other.
- `conftest.py` sits at each level and wires fixtures — test functions receive objects, not construction code.

**Why does this direction prevent pain?**

When layers only depend downward, you can rewrite any layer without touching the ones above it. If the ReqRes API changes its auth header, you fix `api/client.py` and every test automatically gets the fix. If you hardcoded the auth header in 30 test functions instead, you would edit 30 files — and miss one.

Circular imports are the most common mistake in growing frameworks. If `api/client.py` imports from `utils/assertions.py` AND `utils/assertions.py` tries to import something from `api/`, Python raises `ImportError: cannot import name` at collection time — before any test runs. The solution is always: move shared code down to the layer that nothing depends on.

**Why data factories beat hardcoded test data:**

Hardcoded email addresses like `"testuser@example.com"` cause false failures. If you ran the test yesterday and the user was created in the database, today's test fails because the email already exists — not because your code is broken. A factory generates a unique value per run (`uuid4` suffix), so tests are independent and can run in parallel. When a field becomes required (e.g., the API now requires a `phone` field), you update the factory once and every test that calls `make_test_user()` is fixed automatically.

**Why `utils/assertions.py` matters:**

Standard `assert response.status_code == 200` prints `AssertionError` with no context. A wrapper prints `"Expected status 200, got 422. Body: {'detail': 'email already registered'}"`. The response body is the signal you need to understand the failure — without it you add a `print()` statement, re-run the test, and read the terminal output manually. Good failure messages eliminate that loop.

**Key conventions — summarised:**

1. Test files only import from `api/`, `pages/`, and `utils/` — never from other test files.
2. API clients and page objects never import from each other.
3. Fixtures handle all setup and teardown — test functions only call and assert.
4. `pytest.mark.parametrize` lives at the test layer, not inside API clients.
5. Every fixture that creates data in an external system must clean it up in a `yield` fixture teardown.

**Tại sao phân lớp quan trọng — đồ thị phụ thuộc:**

Bốn lớp tạo thành chuỗi phụ thuộc một chiều nghiêm ngặt:

```
utils  ←  api / pages  ←  tests
                ↑
           conftest.py
```

- `utils` không import từ module dự án nào — nó là Python thuần túy.
- `api` và `pages` import từ `utils` nhưng không bao giờ từ `tests`.
- `tests` import từ `api`, `pages` và `utils`. Không bao giờ từ nhau.
- `conftest.py` nằm ở mỗi cấp và kết nối các fixture.

**Tại sao hướng này ngăn ngừa vấn đề?**

Khi các lớp chỉ phụ thuộc xuống dưới, bạn có thể viết lại bất kỳ lớp nào mà không cần chạm vào các lớp phía trên. Nếu API ReqRes thay đổi header xác thực, bạn sửa `api/client.py` và mọi test tự động nhận được bản sửa lỗi. Import vòng tròn là lỗi phổ biến nhất trong framework đang phát triển — Python sẽ báo `ImportError` ngay khi thu thập test, trước khi bất kỳ test nào chạy.

**Tại sao data factory tốt hơn dữ liệu hardcode:**

Email hardcode như `"testuser@example.com"` gây ra lỗi giả. Nếu bạn chạy test hôm qua và người dùng đã được tạo trong cơ sở dữ liệu, test hôm nay thất bại vì email đã tồn tại — không phải vì code của bạn bị lỗi. Factory tạo ra giá trị duy nhất mỗi lần chạy (hậu tố `uuid4`), vì vậy các test độc lập và có thể chạy song song.

**Tại sao `utils/assertions.py` quan trọng:**

`assert response.status_code == 200` tiêu chuẩn in `AssertionError` không có ngữ cảnh. Wrapper in `"Expected status 200, got 422. Body: {'detail': 'email already registered'}"`. Nội dung response là tín hiệu bạn cần để hiểu lỗi — không có nó bạn thêm `print()`, chạy lại test và đọc đầu ra terminal thủ công.

**Quy ước quan trọng — tóm tắt:**

1. File test chỉ import từ `api/`, `pages/` và `utils/` — không bao giờ từ file test khác.
2. API client và page object không bao giờ import từ nhau.
3. Fixture xử lý toàn bộ setup và teardown — hàm test chỉ gọi và assert.
4. `pytest.mark.parametrize` nằm ở lớp test, không phải bên trong API client.
5. Mọi fixture tạo dữ liệu trong hệ thống bên ngoài phải dọn sạch trong teardown `yield`.

# utils/assertions.py
from jsonschema import validate, ValidationError
import requests
from typing import Any


def assert_status(response: requests.Response, expected: int) -> None:
    """Assert HTTP status code with a descriptive failure message."""
    assert response.status_code == expected, (
        f"Expected status {expected}, got {response.status_code}.\n"
        f"URL: {response.request.method} {response.url}\n"
        f"Body: {response.text[:300]}"
    )


def assert_schema(data: Any, schema: dict, label: str = "") -> None:
    """Validate a dict/list against a JSON Schema, raising AssertionError with path info."""
    try:
        validate(instance=data, schema=schema)
    except ValidationError as e:
        path = " -> ".join(str(p) for p in e.absolute_path) or "(root)"
        raise AssertionError(
            f"Schema validation failed{f' for {label}' if label else ''}.\n"
            f"Path: {path}\n"
            f"Message: {e.message}"
        ) from e


def assert_response_ok(
    response: requests.Response,
    schema: dict | None = None,
    label: str = "",
) -> dict:
    """Assert 200 status, parse JSON, optionally validate schema. Returns parsed body."""
    assert_status(response, 200)
    data = response.json()
    if schema:
        assert_schema(data, schema, label=label or response.url)
    return data


def assert_field_equals(data: dict, field: str, expected: Any) -> None:
    """Assert a field value in a response dict with a clear message."""
    assert field in data, f"Field '{field}' not found in response. Keys: {list(data.keys())}"
    actual = data[field]
    assert actual == expected, (
        f"Expected data['{field}'] == {expected!r}, got {actual!r}"
    )


def assert_no_sensitive_data(response: requests.Response) -> None:
    """Assert no credentials or stack traces leak in error responses (status >= 400)."""
    if response.status_code < 400:
        return
    text = response.text.lower()
    forbidden = ["password", "secret", "token", "stack trace", "traceback", "syntax error"]
    for keyword in forbidden:
        assert keyword not in text, (
            f"Possible sensitive data leak: '{keyword}' found in {response.status_code} response.\n"
            f"Body snippet: {response.text[:200]}"
        )
```

# utils/data_factory.py
import uuid
import time
from dataclasses import dataclass, field


@dataclass
class UserData:
    """Immutable value object representing a user for test input."""
    email: str
    password: str
    role: str = "viewer"
    name: str = ""

    def to_dict(self) -> dict:
        return {
            "email": self.email,
            "password": self.password,
            "role": self.role,
            "name": self.name,
        }


@dataclass
class PostPayload:
    """Immutable value object representing a post body for test input."""
    title: str
    body: str
    user_id: int

    def to_dict(self) -> dict:
        return {"title": self.title, "body": self.body, "userId": self.user_id}


def _uid() -> str:
    """Return 8-char hex unique suffix."""
    return uuid.uuid4().hex[:8]


def make_unique_email(prefix: str = "test") -> str:
    """Return an email guaranteed unique per process run."""
    return f"{prefix}+{_uid()}@example.com"


def make_test_user(role: str = "viewer") -> UserData:
    """
    Create a UserData with a unique email.

    Why unique? If the API enforces unique emails and you run tests twice,
    the second run fails with 409 Conflict — not because your code broke,
    but because hardcoded data collides. uuid4 suffix eliminates that class
    of false failure entirely.
    """
    return UserData(
        email=make_unique_email(role),
        password="TestPass123!",
        role=role,
        name=f"Test {role.capitalize()} {_uid()}",
    )


def make_post_payload(
    title: str | None = None,
    user_id: int = 1,
    body: str | None = None,
) -> PostPayload:
    """
    Build a PostPayload with a timestamp-based title if not provided.

    Timestamps keep test data readable in the API logs: you can grep
    for the exact second a test ran and find the created resource.
    """
    return PostPayload(
        title=title or f"Test Post {int(time.time())} {_uid()}",
        body=body or "Automated test post. Safe to delete.",
        user_id=user_id,
    )
```

# api/client.py
import requests


class ApiClient:
    """
    A thin wrapper around requests.Session.

    Why a wrapper and not bare requests.get()?
    - The base URL and default headers are configured once here.
    - Switching from reqres.in to a staging URL means changing one constant.
    - The session reuses TCP connections, which speeds up large test runs.
    - You can add auth headers (Bearer token, API key) to __init__ without
      touching any test file.
    """

    def __init__(self, base_url: str = "https://reqres.in/api") -> None:
        self._base_url = base_url.rstrip("/")
        self._session = requests.Session()
        self._session.headers.update({"Content-Type": "application/json"})

    def get(self, path: str, **kwargs) -> requests.Response:
        return self._session.get(f"{self._base_url}{path}", **kwargs)

    def post(self, path: str, **kwargs) -> requests.Response:
        return self._session.post(f"{self._base_url}{path}", **kwargs)

    def put(self, path: str, **kwargs) -> requests.Response:
        return self._session.put(f"{self._base_url}{path}", **kwargs)

    def patch(self, path: str, **kwargs) -> requests.Response:
        return self._session.patch(f"{self._base_url}{path}", **kwargs)

    def delete(self, path: str, **kwargs) -> requests.Response:
        return self._session.delete(f"{self._base_url}{path}", **kwargs)

    def close(self) -> None:
        self._session.close()


# api/endpoints/posts.py
from api.client import ApiClient
import requests


class PostsEndpoint:
    """
    Endpoint wrapper for /posts resources.

    This class has NO assertions and NO test logic. It only:
    1. Knows the URL pattern for each operation.
    2. Forwards the raw requests.Response to the caller.

    Tests decide whether a 404 is a failure or an expected outcome.
    The endpoint class must never make that decision.
    """

    def __init__(self, client: ApiClient) -> None:
        self._client = client

    def get(self, post_id: int) -> requests.Response:
        return self._client.get(f"/posts/{post_id}")

    def list(self, **params) -> requests.Response:
        return self._client.get("/posts", params=params)

    def create(self, payload: dict) -> requests.Response:
        return self._client.post("/posts", json=payload)

    def update(self, post_id: int, payload: dict) -> requests.Response:
        return self._client.put(f"/posts/{post_id}", json=payload)

    def delete(self, post_id: int) -> requests.Response:
        return self._client.delete(f"/posts/{post_id}")
```
